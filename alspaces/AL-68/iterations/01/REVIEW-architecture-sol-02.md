## Blocking finding

### ARCH02-1 — P2: Child recovery has no continuation past a repeatedly selected first page

Locations: `backend/internal/adapters/capture/children.go:139`, `:146`, `:161`, `:176`; `backend/internal/adapters/opencode/capture_snapshot.go:126`.

The new bounded recovery path limits its initial selection but does not advance that selection. OpenCode always queries the first `LIMIT remainingSessions` children ordered by ID. Already inherited children are skipped after the query, so they permanently occupy the page and later source-proven children never become candidates. The registration refresh cursor does not repair this: it operates only after recovery and only on owners already bound to the ticket. Final fixed-point propagation also requires an accepted child snapshot, which the excluded unassigned child never receives.

Executed production-path reproduction using the native `bin/agentic-lens-linux-amd64` produced by the parent's corrected build, with isolated SQLite/source/state files at `/tmp/al68-arch02-children-16omngys`:

- Created a supported v1 SQLite layout containing `root` and native children `child-a`, `child-b`, `child-c`, each with valid assistant usage. Source `parent_id` for all three children is exactly `root`.
- Explicitly bound only `root` to TEST-100 through request/bind. Registered `child-c` locally without guessing its ticket, representing its independently delivered callback/agent-context request.
- Ran eight separate native `capture reconcile --ticket-id TEST-100 --max-sessions 2` passes with the default byte budget. Every pass returned only root/a/b as ticket owners and `pending_children: 0`; local status after the eighth pass still showed `child-c` unassigned while root/a/b were current.

This is not merely a deliberately small-budget partial pass. Repeating the documented continuation cannot reach the omitted owner. The same trigger occurs at the default limit for a parent with more than 256 direct children, and configured smaller limits are explicitly supported. It can also affect later children under multiple parents when earlier recovery spends part of the shared budget. The generic coverage disclaimer cannot replace a recoverable pending route for a locally registered, source-proven child.

The Codex queued-stop branch has the corresponding starvation defect. It always selects pending paths in the same order with `LIMIT budget.sessions`; failed or mismatched metadata is retained without advancing a queue cursor. In a second isolated native fixture, `/tmp/al68-arch02-codexqueue-4u93qz1k`, a bound root had an accepted snapshot, then received three SubagentStop paths: two alphabetically earlier malformed metadata files and one valid source child whose metadata names that root. Four separate two-session passes each retried only the malformed files, returned only the root, and left all three paths pending. The valid child and ordinary root refresh never received work. This is reachable when one child's source remains malformed or has not flushed; unrelated successful child recovery must still progress.

Required correction: give both child-selection paths recoverable progress across bounded passes, including pages containing known children and failing metadata. Preserve source/store/parent proof and do not bind arbitrary unassigned roots. Retain pending/incomplete coverage when discovery has not exhausted the source children. Add isolated regressions with more children than one pass permits and with failed metadata ahead of a valid queued child, asserting eventual inherited capture across successive passes. This is one continuation/fairness finding in the CAP-04/05/11 correction area, not a request for broader redesign.
