# AL-84: Adopt OpenSpec across the platform and repository

## Goal

Deliver one usable OpenSpec workflow for AgenticLens itself and adopting repositories: a ticket-prefixed change is the single home for planning, delivery evidence and telemetry, and remains readable and refreshable after archive.

## Context

The [PO-24 assessment](../../PO-24/ASSESSMENT.md) confirmed that configuration can discover ledgers inside OpenSpec changes, but detail readers and publishers reconstruct a direct path from the ticket ID. Multiple roots alone cannot follow archive renames or prevent active-folder recreation. Repository agents, skills and backlog still assume separate alspaces ticket folders. This ticket delivers the complete adoption outcome in one slice, as explicitly requested by the user; platform support without the repository/guidance cutover is incomplete.

## Acceptance criteria

- Support multiple explicit shared workspace roots, including OpenSpec active/archive directories and existing historical records. Provide bounded immediate-child discovery for the new mode; retain existing single-root recursive configuration and explicit-override behavior. Missing, invalid or contradictory policy fails clearly rather than selecting an invented root.
- All workspace consumers use one stable-identity/location resolution contract: listing, detail, configured artifacts, events/traces, comparison, live workspace selection, manual default destination selection and automatic publication. Moving a known change between configured roots preserves its identity, supported facts and ordinary access.
- Create OpenSpec changes from explicit configured canonical ticket IDs plus descriptions, for example canonical `AL-123` with folder `al-123-add-login`. Preserve canonical spelling separately from mutable folder names. OpenSpec already accepts this lowercase naming convention; use supported setup/creation extension points rather than requiring an upstream fork or an unverified hook. Reject invalid names/prefixes, collisions and conflicting folder/ledger identity without overwriting content.
- Existing valid ledgers supply recorded ticket identity. Ledger-free known changes can be resolved through explicit naming/creation association for first publication. Require one change per canonical ticket within the selected project; multiple distinct matches are actionable conflicts, not permission to select the first root, merge facts or silently prefer an active folder.
- Physical aliases/overlapping roots cannot enumerate one directory twice. Archive containers and nested spec folders are not tickets in immediate-child mode. An unavailable root produces partial-result diagnostics while valid sibling roots remain usable. Expose location/conflict/recovery context consistently in CLI, API and dashboard; absent telemetry is unavailable, not measured zero.
- In managed OpenSpec mode, publish only inside a unique existing change. AgenticLens may initialize its ledger there but never create a missing change directory. Explicit output paths must agree with the resolved change and cannot bypass containment or missing-parent checks. Preserve supported explicit initialization/output behavior for legacy single-root projects.
- Refresh an archived change's existing ledger without reactivating it or creating an active sibling. Concurrent archive/move and interrupted publication must yield one valid update or an explicit recoverable retry, with no lost history, duplicate outputs or recreated parents. Verification must exercise real filesystem movement rather than only compare path strings.
- Keep exact source/session bindings attached to the canonical ticket within the existing project/worktree boundaries, independent of the selected root. Folder moves need no rebinding; multiple roots do not permit ownership reassignment across worktrees. Preserve unavailable/partial owners, other contributors/harnesses and legitimate multiplicity; complete local refresh remains authoritative and repeated refresh remains idempotent.
- Extend setup/operator workflows with a supported, verified and pinned OpenSpec option while retaining non-OpenSpec adoption. Configure the active/archive roots and standard proposal/design/tasks paths in place, without a separate per-ticket AgenticLens workspace. Preserve unrelated/custom instructions, skills and configuration; retain existing setup confirmation requirements and distinguish shared policy from local source/capture state.
- Demonstrate source-backed Codex/OpenCode telemetry in the created change with explicit conventional type, exact ownership and honest missing-source/cost behavior. OpenSpec's other assistant integrations must not be advertised as new AgenticLens source adapters. Record the tested CLI/schema release; unknown fields and advisory naming rules cannot be presented as enforced behavior.
- Reconcile AGENTS.md, relevant technical/regression rules, shared personas/references, Codex registrations, applicable OpenCode setup, every affected AgenticLens skill/template, and setup/operator/contributor documentation. Search active sources for conflicting path/lifecycle rules and correct the owning source; preserve unrelated historical audits.
- Use one authoritative set of OpenSpec artifacts for proposal/acceptance, technical design, tasks, delivery/review evidence and telemetry. Remove parallel independently maintained plans/contracts/backlog truth. Preserve planning-only PO sessions, approval before coding, specialist role boundaries, model/review attribution, required verification, final telemetry and PR handoff. Planning readiness, checkbox completion, approved scope and verified delivery remain distinct.
- Cut over the live AgenticLens repository to the verified OpenSpec structure/schema and multi-root configuration. Future PO/GEN/development work uses one ticket-prefixed OpenSpec change home. Retain an explicit legacy root for historical alspaces records, with appropriately bounded discovery; do not require new alspaces ticket workspaces after cutover.
- Migrate remaining active roadmap specifications into OpenSpec while preserving ticket IDs, acceptance, readiness/dependency information and active-owner boundaries. Provide one editable backlog with a navigable dependency/readiness view and update contributor entrypoints. Coordinate active owners before moving writable artifacts; preserve navigation to existing public/historical evidence and leave historical facts intact.
- Provide a reviewed migration inventory and recoverable cutover. Failure preserves the prior supported configuration/history and exposes partial progress. Do not duplicate ledgers, silently reticket sessions, rewrite completed audits or depend on original session stores/private capture receipts for historical reads.
- Demonstrate the complete selected workflow: planning, scope change, explicit implementation approval, native source capture/publication, dashboard/CLI detail, retained incomplete-review evidence, completion, OpenSpec archive and late refresh. Include copied-history reads without original sources and confirm no guidance/writer recreates the retired workspace convention. Text searches or synthetic fixtures alone do not establish native runtime compatibility.

## Implementation notes

[PO-24 SPEC.md](../../PO-24/SPEC.md) owns the initiative context; this ticket owns implementation acceptance. This is one delivery slice, not a set of independently completable sub-tickets. Concrete configuration syntax, resolver contracts and supported custom-schema design belong to the developer contract. Preserve the [portable ledger contract](../../../TECHNICAL_GUIDELINES.md#portable-ledger-contract) and relevant [regression boundaries](../../../docs/REGRESSION_PREVENTION.md).

AL2-2 retains ownership of compressed archive packages and their precedence rules; OpenSpec archive folders need no package archiver. AL-81 independently separates manual generation from capture-registry access; do not reintroduce that dependency or weaken automatic ownership. Coordinate shared worktree/capture paths with AL-80 without taking its scope. Cross-repo OpenSpec stores, additional harness adapters, dynamic capability/spec-glob browsing and phase/progress analytics are not required for this adoption slice.
