## Frozen implementation contracts

The following routine design decisions finalize the approved requirements before coordinated implementation. They supersede the earlier references to unresolved interface design, without changing acceptance.

**Name representation.** Use the exact configured project_name. A name of 1–120 UTF-8 bytes that matches portable ASCII letters/digits followed by letters/digits/dot/underscore/hyphen can be literal, except dot components and Windows reserved basenames (including extensions). Encode other valid names as a leading ~ plus lowercase hexadecimal UTF-8 bytes, bounded to 241 characters. The literal alphabet excludes ~, preventing encoding collisions. Reject blank/invalid UTF-8/overlong names. Store and compare the exact name in project metadata before any operational access; an existing case-insensitive filesystem alias with different metadata is a visible conflict, never a second project silently opening the same state.

**Storage and typed locations.** ProjectState(base, project) resolves the required configured name through the canonical configuration boundary and returns only its logical registry directory; no basename/path-hash fallback. OpenProject(logicalDirectory, project) opens schema2, validates the exact logical name and canonical worktree, and returns a scoped Store. A worktrees table assigns an integer ID to each unique canonical physical directory. Every operational SQL table, query, primary/unique key, diagnostic lookup/index and cursor includes this worktree ID. Preserve one engine with explicit scoped SQL parameters; do not introduce SQL text rewriting or a second scheduler. Global diagnostic sequence numbers are permitted only with scope-qualified selection and acknowledgements.

Store.RegistryDirectory() identifies the logical database directory. Store.CoordinationDirectory() identifies its worktrees/<decimal-ID> directory for worker locks/status/logs, source manifests and disablement. Callbacks pass the logical registry as state-dir. StateLocation carries RegistryDirectory, CoordinationDirectory and WorktreeID explicitly. A compatibility helper may accept an existing coordination path only after validating its recorded logical registry and exact physical worktree; the actual database open still targets RegistryDirectory. No production implicit owner fallback is permitted. Installer allocation precedes first manifest writing. Read-only opening looks up an existing scope without inserting one; absent scope is absent-state diagnostics, not permission to create it. Low-level test helpers must not supply production project-name or ownership fallbacks. Exact artifact publication locks remain keyed to the physical ledger destination.

Separate protocol responsibilities: registry schema2, installation manifest2 for changed state/coordination meaning, and handler capability3 for the new required location/configuration behavior. Keep ledger5. Upgrade checks and both downloaders must distinguish these constants rather than reuse one version number for unrelated contracts.

**Explicit updater.** Add init --update-capture-config, with --dry-run and an optional explicitly supplied --capture-state-dir. This narrow mode reads existing raw configuration and fills a missing state_dir without requiring new-project flags or replacing unrelated content. An explicitly supplied path requests replacement; preserving or migrating existing populated state is mandatory before activation. It is not an init --force shortcut. Keep local overrides and incomplete/raw-update parsing separate from successful operational loading.

**Explicit relocation.** Add capture relocate-state --from-state-dir <exact-old-directory> --to-state-dir <base>, with --dry-run. The current configured project/name and exact source ownership authorize only that worktree. A dry run performs no migrations or writes. Actual relocation obtains the source worker lock, exact known ticket publication locks in deterministic order, and a bounded SQLite writer reservation. A held live worker or busy source transaction refuses migration with retry guidance; no process killing or waiting without a bound.

Persist a relocation journal/ID and recoverable source backup before committing the fence. For the inspected supported schema1 family, materialize known lazily created tables, install abort-on-insert/update/delete triggers on all mutable legacy tables, and set a negative retired capture_meta marker in the same source transaction. New old-native opens fail the existing version guard; triggers also reject already-open old handles. Unknown legacy layouts/protocols refuse cutover. This fence is a concrete design to verify against the actual prior native and already-open connections, not a compatibility claim for arbitrary old writers.

Commit the source fence before copying/importing its now stable records into a migration-pending destination worktree scope. Preserve the old database and backup; never replace it with an empty forwarding registry. A special known-schema reader can import fenced records, but ordinary readers/writers cannot bypass protocol validation. Validate the imported scope, configuration update and unchanged-owned integration refresh; then activate the destination with the migration ID in its own transaction. The journal records completion afterward. A crash after fencing leaves source plus staged destination resumable. No cross-database/configuration atomic commit is claimed. Once destination activation may have accepted new writes, recovery rolls forward; it must not unfreeze the old source or discard destination writes. Any pre-activation rollback must prove no destination writes were accepted and retain the backup. Failures during explicit maintenance are loud and cannot acknowledge lost callbacks.
