## Problem remaining after delivered dependencies

Historical skill/task recovery already exists but its safe refresh and completeness semantics have gaps. The remaining useful work is a narrowly bounded correction to source-backed backfill, not a second schema-v4 introduction. This finding is based on source inspection, not a reproduced failure or completed test run.

## Observed remaining gaps

1. Canonical v4 with no migration metadata can hit the completed fast path even when `RecomputeDB` is explicitly requested. The skip guard checks `RecomputeGit` but not `RecomputeDB`. The similarly named existing recompute test supplies completed migration metadata and therefore misses the ordinary canonical case.
2. In partial OpenCode resolution, backfill assigns the entire ledger-level skills/task arrays from only the refreshed sessions, then preserves unresolved sessions separately. Old facts belonging to unavailable roots can be lost. These fact types have no session/source identifier, so individual old rows cannot safely be attributed using timestamp, role, turn or task child ID.
3. A single `dbSessionFound` boolean represents aggregate recovery. Any successful Codex tree sets it true, and either harness can therefore clear the global pending `source_backfill` step despite other selected stored roots or children being unavailable. Root-count comparison in OpenCode also does not independently establish stored-child coverage.
4. Existing tests cover migration/source separation, unavailable sources, multi-root extraction, source filtering and Codex tree replacement. No skill/task assertions occur in `backfill/engine_test.go`; recovery multiplicity and preservation of these arrays through incomplete refresh remain unguarded there.

## Accepted implementation boundaries

Retain schema v4 and optional arrays at the serialization boundary. Internally, skill/task collections are required empty-or-populated arrays after ledger-file reading, as clarified below. AL-55 owns that read normalization, backfill command selection, safe source refresh, preservation of historical skills/task facts, and truthful recovery outcome. It does not own cost availability, rate cards, UI simulation, a new schema family, or AL-43 diagnostics/content fields.

An explicit source recompute must reach the requested source for an otherwise complete canonical ledger without requiring `--force`. Routine invocation without recompute retains existing skip semantics. Existing force and heuristic discovery are separate controls; exact stored session identity remains the default, and heuristic substitution remains opt-in.

Resolve and parse each selected source tree before replacement. Successful refresh replaces cumulative snapshots for that owner rather than adding totals. Preserve unavailable sessions, all non-selected harness sessions, legitimate repeated invocation rows, parent links and existing persisted facts when discovery, parsing or grouping fails. Confirm stored-child coverage as well as roots; source absence is incomplete, not a successful empty extraction.

Accepted conservative array policy: the current producer is explicitly OpenCode-owned, but historical ledger-level rows have no independently verifiable owner. Replace the whole skill/task arrays only after complete exact refresh of all stored OpenCode roots and children required to reconstruct that producer's history. On incomplete OpenCode recovery preserve both old arrays unchanged and report incomplete recovery; do not append an unattributable fresh subset or guess ownership. Codex-only refresh never manufactures or replaces skill/task facts. A successful complete OpenCode recovery with no observed invocations may produce an empty optional collection; absence alone never establishes that condition. This policy avoids a speculative persisted provenance extension; partial fresh skill/task enrichment is intentionally deferred until full history is available.

Independently complete available session trees may refresh while skill/task arrays remain the prior snapshot. Diagnostics must explicitly say those arrays were retained because recovery was incomplete; they must not claim the arrays reflect the refreshed sessions. The user accepted this mixed-age limitation; diagnostics must acknowledge both refreshed sessions and retained older collections in the per-ticket result and command summary. A tree missing a previously known child is incomplete and must remain entirely unchanged, including that child. Ownerless arrays with unknown, ambiguous or zero eligible reconstructible OpenCode owners remain unchanged and unresolved rather than becoming empty. Stage extraction results before modifying the persisted aggregate: a late parse/grouping failure cannot publish replacement arrays based on the earlier successful subset. Completeness means successful exact discovery and parsing of every required stored root and descendant, plus grouping of the complete discovered tree; a nonempty returned slice or root count is insufficient. A source-confirmed successful zero-observation result is distinct from failed discovery or unavailable source.

Track coverage per selected harness/tree during execution. Clear a pre-existing global source-backfill requirement only when all stored owners required by that requirement are demonstrably covered; a success from one harness must not discharge missing owners in another. Report missing source/tree and parse/grouping failures with useful context. Preserve pending steps unrelated to the successful owner. Do not impose permanent migration metadata on already-complete canonical data merely because optional skill/task arrays are absent. Failed optional refresh of valid canonical baseline data reports an incomplete command outcome while preserving runtime eligibility; it must not create a new mandatory migration. A pending global obligation includes all stored required owners across sources, even when the selected source is narrower. Unknown or ambiguous required owner attribution prevents positive completion. Completeness is bounded by known stored owners and discovery results; no exhaustive external history claim is authorized.

Persist only after final domain preparation and boundary validation succeed. Keep dry-run free of file changes. Repeated unchanged refresh preserves the semantic fact set and row multiplicity; administrative timestamps may advance under current behavior. No read hydration or GET persistence changes are proposed. Preserve integrated AL-43 F3 additive warning reconciliation, F4 bounded structured-output classification and original raw evidence. Preserve the AL-47 SSE startup-subscription ordering regression and source/content metadata throughout refresh and persistence.

## Resolved acceptance decisions

Source: explicit user instruction "continue with AL-55 implementationc", conveyed by MGT-1 through the parent orchestrator; PO-17 proposal `64b7d1f:alspaces/PO-17/AL-55_ACCEPTANCE_PROPOSAL.md` supplies the five reconciled recommendations. No new iteration is needed: these choices resolve the pending scope rather than introduce a new feature boundary.

1. Keep optional v4 skill/task arrays at the wire/file boundary. Missing, null and empty forms remain compatible. After an actual ledger-file read, internal skills/task collections must be non-null empty-or-populated arrays: default omitted or null collections to empty arrays, preserve populated rows and their multiplicity, and reject malformed present collection shapes through existing validation rather than silently defaulting them. This is internal normalization, not a required wire-array tightening, version bump, client migration or permanent marker. Empty defaults never prove source recovery, successful empty observation, completeness or migration completion, and must never erase populated ownerless history.
2. Refresh independently complete trees while retaining both whole ownerless arrays semantically unchanged whenever any required OpenCode owner/descendant is unavailable, incomplete, unknown or not reconstructible. Never guess ownership or erase arrays because no eligible owner exists. Replace the arrays only after complete source-backed recovery. Accept mixed recovery ages and expose them explicitly in ticket and command-summary diagnostics.
3. Clear an existing global source-backfill requirement only when all stored required owners across sources have successful exact discovery, parsing, grouping and validated recovery. Preserve unrelated pending steps and missing-child facts. Optional refresh failure preserves eligibility of valid already-complete canonical baseline data and does not create a new migration requirement.
4. Explicit RecomputeDB refreshes complete cumulative snapshots without Force, including skill/task arrays when decision 2 allows; event-only updates do not satisfy recomputation. Routine invocation keeps routine skips. Force never relaxes preservation or ownership guarantees; heuristic discovery remains separately opt-in. CLI help must explain these semantics consistently.
5. Keep current backup interfaces: standalone migrate backup/dry-run; backfill dry-run and atomic replacement. No new backfill backup interface. Atomic replacement is neither rollback nor protection against semantic loss. Manual backup may be documented as an operator option, without claiming migrate --backup necessarily copies an already-current ledger.

Preserve nullable-cost and rate-card allocation for PO-17/manager and held AL-57.
