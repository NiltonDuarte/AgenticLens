AL-84: Support flexible workspace layouts and adopt OpenSpec

Goal

Let users organize and bind tickets in any explicitly configured workspace directories through one lean platform capability. Use that capability to deliver the repository’s complete OpenSpec workflow, with planning, evidence and telemetry in the same change home before and after archive.

Context

The PO-24 assessment confirmed that configuration can discover ledgers inside OpenSpec changes, but detail readers and publishers reconstruct a direct path from the ticket ID. Multiple roots alone cannot follow archive renames or prevent active-folder recreation. Users also need ordinary layouts such as alspaces/archive, alspaces/al, alspaces/al2, alspaces/po, alspaces/fix and documentation folders, alone or together with an OpenSpec tree. These directories are equal first-class workspaces, not compatibility roots or OpenSpec-specific modes. Repository agents, skills and backlog still assume a single ticket root. This ticket delivers the complete adoption outcome in one slice, as explicitly requested by the user; platform support without the repository/guidance cutover is incomplete.

Acceptance criteria

  • Support one or many explicit user-selected workspace directories through the same configuration/discovery/binding model. Existing single-directory input normalizes to that model, not a separate compatibility implementation. Folder names, grouping, depth and ticket-prefix/type associations are user decisions: no reserved alspaces/OpenSpec paths, obligatory layout or inferred routing. Missing, invalid or contradictory policy fails clearly rather than selecting an invented root.
  • Accept configured roots at arbitrary depths with explicit bounded discovery scope sufficient for direct and nested layouts. Enumerating immediate children is available where the user selects container roots; do not force shallow discovery on every workflow. Demonstrate plain alspaces, its archive, prefix/type-grouped folders, arbitrary renamed folders, OpenSpec changes/archive and a mixture of them in one selected project. No code changes or special fallback mode are needed when the user reorganizes those configured paths.
  • All workspace consumers use one stable-identity/location resolution contract: listing, detail, configured artifacts, events/traces, comparison, live workspace selection, manual default destination selection and automatic publication. Moving a known workspace between configured roots preserves its identity, supported facts and ordinary access.
  • Create OpenSpec changes from explicit configured canonical ticket IDs plus descriptions, for example canonical AL-123 with folder al-123-add-login. Preserve canonical spelling separately from mutable folder names. OpenSpec already accepts this lowercase naming convention; use supported setup/creation extension points rather than requiring an upstream fork or an unverified hook. Reject invalid names/prefixes, collisions and conflicting folder/ledger identity without overwriting content.
  • Existing valid ledgers supply recorded ticket identity. Users can bind a known canonical ticket to an explicitly selected existing directory even when its name does not contain the ticket ID. Ledger-free workspaces use explicit creation/binding association or a user-selected naming policy for first publication; the OpenSpec prefix convention is one such policy. Multiple distinct matches require explicit user selection/association, not first-root precedence, automatic merging or preference for an active-looking folder.
  • Physical aliases/overlapping roots cannot enumerate one directory twice. Container folders and nested spec folders are not tickets merely because they are directories. Discovery follows the selected scope and actual workspace identity/evidence. Folder labels such as archive, docs or fix do not establish completion dates, ticket type or write policy. An unavailable root produces partial-result diagnostics while valid sibling roots remain usable. Expose location/conflict/recovery context consistently in CLI, API and dashboard; absent telemetry is unavailable, not measured zero.
  • For any existing bound workspace, publication resolves its actual directory across the configured roots and may initialize/update its ledger there. If the bound target disappears or moves concurrently, report/retry resolution without recreating its old directory. Explicit output paths must agree with the selected binding and containment policy. New workspace creation remains an explicit user operation with a selected destination or unambiguous user-configured routing rule; never invent a root or infer prefix routing from directory names. OpenSpec owns creation of its change folders through its setup workflow.
  • Moving a workspace into a user-selected archive directory changes no lifecycle facts by itself. Refresh its existing ledger without creating a sibling at the former location; for an OpenSpec-archived change, refresh must not reactivate the change. Concurrent archive/move and interrupted publication must yield one valid update or an explicit recoverable retry, with no lost history, duplicate outputs or recreated parents. Verification must exercise real filesystem movement rather than only compare path strings.
  • Keep exact source/session bindings attached to the canonical ticket within the existing project/worktree boundaries, independent of the selected root. Folder moves need no rebinding; multiple roots do not permit ownership reassignment across worktrees. Preserve unavailable/partial owners, other contributors/harnesses and legitimate multiplicity; complete local refresh remains authoritative and repeated refresh remains idempotent.
  • Extend setup/operator workflows to configure and explain user-selected roots, discovery scope, ticket binding and optional explicit creation routes without prescribing directory names. Add a supported, verified and pinned OpenSpec setup that uses these same core capabilities. Configure its selected changes/archive roots and standard proposal/design/tasks paths in place, without a separate per-ticket AgenticLens workspace. Preserve unrelated/custom instructions, skills and configuration; retain existing setup confirmation requirements and distinguish shared policy from local source/capture state.
  • Demonstrate source-backed Codex/OpenCode telemetry in the created change with explicit conventional type, exact ownership and honest missing-source/cost behavior. OpenSpec’s other assistant integrations must not be advertised as new AgenticLens source adapters. Record the tested CLI/schema release; unknown fields and advisory naming rules cannot be presented as enforced behavior.
  • Reconcile AGENTS.md, relevant technical/regression rules, shared personas/references, Codex registrations, applicable OpenCode setup, every affected AgenticLens skill/template, and setup/operator/contributor documentation. Search active sources for conflicting path/lifecycle rules and correct the owning source; preserve unrelated historical audits.
  • Use one authoritative set of OpenSpec artifacts for proposal/acceptance, technical design, tasks, delivery/review evidence and telemetry. Remove parallel independently maintained plans/contracts/backlog truth. Preserve planning-only PO sessions, approval before coding, specialist role boundaries, model/review attribution, required verification, final telemetry and PR handoff. Planning readiness, checkbox completion, approved scope and verified delivery remain distinct.
  • Cut over the live AgenticLens repository to the verified OpenSpec structure/schema and multi-root configuration. Future PO/GEN/development work uses one ticket-prefixed OpenSpec change home. Keep the repository’s chosen alspaces directories as ordinary configured roots alongside its selected OpenSpec roots, with appropriate discovery scopes. This repository chooses OpenSpec for future work; the platform continues to support actively creating and using alspaces or any other configured layout without deprecation or a compatibility label.
  • Migrate remaining active roadmap specifications into OpenSpec while preserving ticket IDs, acceptance, readiness/dependency information and active-owner boundaries. Provide one editable backlog with a navigable dependency/readiness view and update contributor entrypoints. Coordinate active owners before moving writable artifacts; preserve navigation to existing public/historical evidence and leave historical facts intact.
  • Provide a reviewed migration inventory and recoverable cutover. Failure preserves the prior supported configuration/history and exposes partial progress. Do not duplicate ledgers, silently reticket sessions, rewrite completed audits or depend on original session stores/private capture receipts for historical reads.
  • Demonstrate the complete selected workflow: planning, scope change, explicit implementation approval, native source capture/publication, dashboard/CLI detail, retained incomplete-review evidence, completion, OpenSpec archive and late refresh. Include copied-history reads without original sources, movement between arbitrary configured roots and explicit creation in a user-selected grouped folder. Confirm OpenSpec works through the same read/bind/publish path and no writer recreates a prior location. Text searches or synthetic fixtures alone do not establish native runtime compatibility.

Implementation notes

PO-24 SPEC.md owns the initiative context; this ticket owns implementation acceptance. This is one delivery slice, not a set of independently completable sub-tickets. Concrete configuration syntax, discovery bounds, resolver contracts and supported custom-schema design belong to the developer contract. The root collection and identity/location resolution are generic platform capabilities; OpenSpec integration supplies workflow/naming/artifact guidance instead of a second scanner, binder or publisher. Preserve the portable ledger contract and relevant regression boundaries.

AL2-2 retains ownership of compressed archive packages and their precedence rules; OpenSpec archive folders need no package archiver. AL-81 independently separates manual generation from capture-registry access; do not reintroduce that dependency or weaken automatic ownership. Coordinate shared worktree/capture paths with AL-80 without taking its scope. Cross-repo OpenSpec stores, additional harness adapters, dynamic capability/spec-glob browsing and phase/progress analytics are not required for this adoption slice.
