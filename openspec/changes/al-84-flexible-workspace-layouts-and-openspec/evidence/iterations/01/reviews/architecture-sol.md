## Finding: private recovery ancestry is not durable before public writes

**Severity 7/10; introduced; required contract.** At `backend/internal/adapters/publication_set.go:309`, `BeginPublication` creates the private journal directory with `capture.MkdirPublicationDirectories`, which delegates to ordinary `os.MkdirAll` for private paths (`capture/publication_files.go:168`). `AcquirePublication` also creates `<state>/publication` with ordinary `MkdirAll` (`capture/publication.go:69`). Neither flushes newly created parent directory entries.

The exact first-use chain is `<existing ancestor>/<possibly new state components>/publication/journals/<SHA256(project)>/<transaction>.json`. Even when state/publication already exists, the first transaction for a project can newly create `journals` and `<SHA256(project)>`. `durableReplace(private, body)` flushes the staged journal file, renames it, then flushes **only** `<SHA256(project)>` (`publication_set.go:217–238`). It does not flush `journals` to persist the project directory entry, `publication` to persist `journals`, or ancestors created while initializing state. The following `durableReplace(public pending indicator)` flushes the public workspace directory and returns success, after which callers may overwrite accepted ledger/summary bytes.

A power loss in this first-publication window can therefore leave a durable public pending indicator and changed/truncated members while the private rollback journal is unreachable because one of its newly created ancestor entries did not persist. Recovery on the originating machine then cannot restore the prior accepted set. The indicator honestly blocks reads, but cannot recover the lost backup. This contradicts design.md's requirement to persist the private journal durably before changing visible members. Ordinary process termination, with the filesystem still running, does not demonstrate this failure; this is specifically a power-loss/storage-durability counterexample.

Guards checked: file `Sync` and immediate-parent `Sync` in `durableReplace`; commit's bottom-up synchronization of public nested member directories; private cleanup after public marker removal; strict journal/member validation; absent-state admission errors; held directory roots. None flushes the newly created private ancestry before the public marker/member writes. Required correction: make private directory initialization durable through its first existing ancestor before exposing the pending transaction; propagate failures before public changes. Add an ordering/failure oracle for fresh state and a new project namespace. No destructive crash experiment was performed.

OpenSpec/Node is confined to development/setup tooling.

The actual pinned CLI apply response carries role/approval requirements in its controlling `instruction`, as well as context/guidance. Generated upstream wording therefore does not establish a bypass. Archive/task completion is explicitly separate from roadmap completion.
