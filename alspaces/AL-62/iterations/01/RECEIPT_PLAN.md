## Protocol and API contract

Add explicitly versioned receipt metadata in the capture adapter, preferably a separate per-destination metadata table so existing legacy receipt blobs remain readable and unmodified. A destination record has at most one active generation and one pending generation, each immutable and bounded. Scope every record to the verified worktree, ticket and canonical physical ledger destination. A generation has a unique local publication ID, a digest of the writer's exact ledger artifact, and the exact trusted auxiliary snapshot (including empty snapshots). Generation IDs are publication metadata, never source invocation IDs. Store no transcripts or invented fact provenance. Bound payload size and reject unknown/malformed metadata versions rather than silently interpreting them as empty proof.

Use explicit operations with these responsibilities: load/select destination evidence; migrate validated legacy scoped evidence to the current destination; stage a pending generation; finalize a pending generation. Suggested names are SelectPublicationAuxiliary, MigratePublicationAuxiliary, StagePublicationAuxiliary and FinalizePublicationAuxiliary. Separate receipt metadata from domain ledger schemas. Compute hashes, canonical paths, random generation IDs and SQLite I/O at adapter/CLI boundaries; pure selection/validation helpers may be isolated without adding I/O to domain.

Selection must expose only the receipt generation matching the actual current ledger artifact; do not expose pending and active rows as one combined receipt. Keep accepted registration and committed-history evidence on their existing independently verified paths. Raw ledger bytes may identify a pre-existing trusted generation by digest, but may never manufacture its receipt rows. Unknown destination/digest/state fails closed unless an explicit, independently proved compatibility/recovery operation authorizes a new binding.

## State machine under the existing ledger publication lock

1. Startup retains the current main.go lock and existing validated file recovery. No receipt state is selected or promoted if journal recovery fails. After successful recovery, read the accepted ledger and select its matching trusted generation. Restored L0 selects active R0; pending R1 can be discarded only after complete rollback. If there is no journal because L1's file commit completed, matching pending R1 can be promoted atomically, closing the opposite crash window. A first-publication rollback may restore file absence: do not invent an old receipt or accepted empty ledger; discard only that destination's unfinished pending generation under the validated recovery result.
2. Before beginning the next file journal, require a trusted active receipt for the prior accepted baseline when it has auxiliary facts. Existing proof can be migrated explicitly as below. Preserve R0 unchanged throughout staging.
3. Run existing BeginPublication and trusted ledger/summary writes. Stage durable pending R1 from the already source/committed-authorized facts and the exact written ledger digest before CommitPublication. Stage an empty R1 too; the existing skip-empty helper cannot leave the new protocol without a generation.
4. Commit files using unchanged CommitPublication semantics. Only after it succeeds finalize the exact pending generation atomically. Crash before file commit leaves R0 available for rollback; crash after file commit but before receipt finalization leaves R1 available for startup promotion. Failed sync/removal retains both proofs until the existing recovery result determines which artifact survived.
5. Bound retention per destination, not per ticket globally. A second destination or generation cannot overwrite another destination's active/pending proof. Prune an old generation only when no recoverable publication for that destination still needs it. Handle identical-artifact generations deterministically without selecting a different fact snapshot or inflating multiplicity. Receipt finalization and recovery are idempotent.

## Compatibility clarification: independently proved artifact replacement

Existing approved alternate-registry publication can legitimately replace the same destination with newer metrics, leaving another registry's receipt artifact digest stale. Receipt metadata is auxiliary authority, not new metric authorization. For well-formed metadata with a nonmatching artifact, Select returns a typed mismatch without receipt fallback. A named write-side rebind may proceed only after existing exact baseline authorization succeeds with independent registered snapshots or pinned committed Git evidence, explicitly excluding both bound generations and unbound receipts. Empty auxiliary claims need no fact values but retain all existing owner checks. Rebind requires no pending generation or file marker and the existing publication lock; it records a new association now, not inferred historical permission. Unknown/malformed metadata remains fatal.

This uses the explicit independently proved recovery allowance above and preserves accepted alternate-registry behavior; it does not enlarge source authorization. Tests must distinguish legacy-receipt-only mismatch rejection from independently proved rebind and unproven row rejection. No raw ledger/journal content is proof, and neither a matching digest nor a current owner registration alone authorizes changed fact values.
