# Audit scope and approval

The user's GEN-27 request authorizes verification on current main, disposable native and fixture probes, and recommendations. The coordinator owns this change and the OpenSpec probe. The Codex, OpenCode and publication investigators own separate temporary fixtures. Product behavior, real harness configuration, roadmap and other tickets are outside the writable scope. The active audit stays in place.

The acceptance boundary is an observed lifecycle with reproducible command shapes, a source-attributed capture trace for each harness, and a move/late-publication check. A provider stub can demonstrate native event transport and persistence. Usage from that stub measures only its supplied fixture. Historical delivery claims and source-level paths carry their own provenance. A missing source is a coverage limit.

## Iteration 02 — One-time setup for Codex binding

The user requested one-time setup so a fresh workspace-write agent can bind its ticket without a per-run directory flag. At `a6a115f7`, a grant for the capture directory worked, but it also allowed sandboxed writes to the worker's retained executables. The coordinator rolled back that grant. The user approved a dedicated binding inbox for the installer and worker. The earlier audit evidence applies to its recorded revision.

The Codex user installer owns a dedicated inbox under the effective Codex home. Grant workspace-write access to that directory only. Preserve other user grants, sandbox mode and hook trust. Include directory/configuration changes in preview, installation, migration and recovery, and remove only provably installer-owned permissions at uninstall. Protect the user configuration from concurrent edits and fail closed on conflicting file types or path aliases. OpenCode and existing direct operator commands retain their supported behavior.

The native hook supplies exact source and request context. The sandboxed submission command uses that context to derive a response slot and authenticate the canonical response fields. Use separate derivations for slot naming and response authentication. Neither the slot name nor the envelope contains a reusable bearer challenge. Authenticate the complete ticket ID, title and type and bind them to the expected worktree, native session and request. The worker checks only expected slots for its own known registrations under bounded session, byte and time budgets. It verifies source ownership and current binding state before committing private metadata and scheduling publication. Retry incomplete source verification, preserve prior facts and make repeated accepted submissions idempotent. Treat the inbox as untrusted filesystem input. Handle file type, replacement and symlink hazards without following arbitrary paths, blocking on special files or deleting unrelated entries. The inbox authenticates submitted content against the native request. OS-level confidentiality between processes that already share read access to private source or registry storage is a separate boundary.

The installation coder owns setup, permission editing and migration. The runtime coder owns authenticated submission, callback feedback and worker consumption. The tester owns independent cases for fresh-root binding, edited/replayed records, unsafe file types, preservation of other sessions, restart and installation rollback. The coordinator owns the real settings, integration, review and delivery.

## Iteration 03 — Protected engine for trusted Codex capture

At `30c38fe5`, the coordinator observed that the trusted hook selected the worktree’s `bin/` engine and the workspace-write sandbox could modify it. In response to the proposed change to trusted Codex callbacks, the user approved “Include protected engine selection in GEN-27”. This supersedes project-controlled executable selection for trusted Codex capture, including in development worktrees. The original audit and the isolated inbox acceptance remain in force.

The operator provisions the native engine using the existing manager installation mechanism, which supports exact host artifacts and an explicit SHA-256 digest. Preserve modified or unowned manager installations and report the supported repair path. Establish the engine identity and a physical location from operator-controlled installation data outside the workspace, inbox and sandbox-writable grants. A project may provide capture policy, ticket context and an exact release requirement. It cannot authorize a new engine, install root, executable, manager, or retained worker by naming it in configuration. Check the installation and path authority before the first executable probe. If the protected installation is missing, incompatible, modified, or its authority cannot be established, stop trusted execution with an actionable diagnostic and preserve pending work. Automatic hooks must not install or fetch artifacts.

Apply this selection to both normal and post-submission Codex callbacks and carry its authority through worker launch, restart, handoff and mixed-source coordination. A handoff must verify that the selected protected build supports protected worker selection; an older engine that can return to the workspace selector is incompatible. Keep retained executables in protected storage. Preserve ordinary CLI development routing, explicit operator commands, compatible OpenCode capture, existing hook trust, and portable ledger ownership and history. The manager owns dispatch, the engine owns collection, and the worker maintains bounded execution.

The manager/installer coder owns protected selection and provisioning feedback. The runtime coder owns propagation and handoff. The tester owns native process boundary and compatibility evidence. The coordinator owns native fresh-root acceptance and delivery.
