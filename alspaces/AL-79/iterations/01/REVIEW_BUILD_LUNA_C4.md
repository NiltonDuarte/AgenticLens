## Hypotheses and evidence

- **Native artifact identity before installation writes (BUILD-01):** The installer first calls `RetainExecutable` into a private staging directory, then reads those admitted bytes for planned writes. Retention checks regular-file/executable status, snapshots and confirms the copied content, validates native host format/platform plus capture and dispatch protocols and nonempty build version, and hashes the retained artifact. Installation ownership/mutation planning occurs after admission. The supplied C3 distribution evidence records actual installed-command refusal for incompatible system, wrong-interface and foreign-platform binaries both before initial install and after a valid install, with bytes, modes and directory entries preserved. C4 changed legacy migration, not this admission route. No residual BUILD-01 counterexample found by source trace; these tests are carried evidence, not a new run here.
- **Exact-cache/development selection:** `ResolveEntrypoint` requires shared exact version configuration. `NativePath` selects the host-named development output only when present, rejects it if invalid rather than falling back, and otherwise derives the exact version/host cache path. The common dispatcher uses that resolver for manual commands and callbacks; cache identity is checked against the pin while valid development builds use their actual identity. The C2 Linux implementation/tests and C3 distribution tests remain unchanged in these paths; the earlier scoped review traced both actual callers and found no defect. Installer-only provisioning remains separate from invocation.
- **Immutable worker bytes (DATA-04):** `RetainExecutable` copies from one opened source, checks size/modification identity during the copy, rereads and hashes the opened source before admission, validates the temporary snapshot, and stores it at a content-addressed path. Workers launch from this retained path. The C4 diff does not alter this path; C3 targeted process and Go evidence covers mutation during admission and later replacement of mutable development output. This supports complete retained bytes on the tested Linux path; it does not prove Windows filesystem/runtime semantics.
- **POSIX process ownership (ARCH-04):** Manual native dispatch uses `syscall.Exec` with the selected binary and original arguments/environment, preserving caller PID, inherited descriptors and native signal/exit status. The existing actual-installed-dispatcher POSIX regression described in `DISTRIBUTION_EVIDENCE.md` observes the selected child PID, forwards SIGTERM without an orphan and preserves self-signal status. C4 does not change it. The supplied evidence is an actual Linux process boundary; I did not rerun it.
- **Windows stable activation/hash repair (ARCH-06):** `ActiveDispatcher` constrains the active executable to the install root's content-addressed `native/<hash>.exe`, checks the stable dispatcher and active bytes against the ownership record, and validates the active native header. Installation retains candidate bytes before updating the root-owned pointer. `stableDispatcherHash` preserves the existing launcher hash when the launcher is present, and uses the newly admitted candidate hash when it is missing and recreated. This addresses the earlier hash mismatch by source trace and the cited Windows test oracle. The Windows PowerShell/loaded-image behavior is not established locally: `test_windows_distribution.py` was not executable without a real Windows PowerShell/interop lane. Cross-compilation and static inspection are not runtime proof.
- **PowerShell transport and shipped wrapper consistency (ARCH-05):** Both shipped wrapper files compare byte-identically to their source counterparts (`cmp` returned success). The correction diff routes through the existing `Invoke-NativeTransport` implementation using explicit argument encoding, inherited standard handles and the bounded advisory process-tree path. C3 distribution evidence describes Windows fixtures for empty/quoted/trailing-backslash arguments, Unicode/mixed-newline input and timeout/termination, but explicitly records that these were not run locally. No source-level regression was found; Windows runtime remains a material limit.
- **C4 legacy migration and recovery (BEH-01 / DATA-02):** `legacyUserChanges` now reads the hook file even for an inactive legacy receipt, removes only exact singly attested owned groups, and refuses if any AgenticLens legacy callback remains before activation. The C4 distribution fixture exercises base and linked-worktree migration, an edited owned callback, preservation of unrelated callbacks/state, and the unknown executable callback case. The C3-to-C4 resource discovery correction also rechecks pending root/home journals and legacy resources after their planned leases are acquired, then refuses recovery if the required lease set changed. It replans migration only after recovery and checks leases for the newly planned journal. C4 targeted Go evidence includes `TestUserRecoveryRejectsResourcesAddedAfterDiscovery`, durable-prefix recovery and interrupted-migration controls (all passing in `/tmp/al79-tester-c4/final-targeted.log`). These are relevant current-revision test results, though the broader POSIX distribution suite cited for migration ran at C3 and the C4 test report assigns the unknown-callback distribution assertion to its owner.
