## Recommended minimal vertical slice

Expose bounded per-owner assessments and decisions through the CLI JSON boundary, shared by explicit generation and source-backed backfill. Self-verification can complete within a single generate command; a separate inspection command is optional. Avoid an always-running liveness daemon, universal agent messaging bridge or arbitrary trust flag. These are proposed interface responsibilities; concrete flag/subcommand naming can follow existing CLI conventions without changing acceptance.

1. During generation, inspect the selected owner/interval and return a typed assessment: completed-only, caller-proof-required, read-only-status-available, or unresolved; include source family, target identity, native interval identity, source boundary evidence, available verification methods and concrete limitations. The agent can select supported verification or preserve known facts through explicit typed options; optional inspection can explain capabilities before generation but is not a required challenge round trip. Default unattended work preserves known values and reports unresolved evidence rather than waits indefinitely or silently trusts it.
2. For current-caller verification, the agent issues a fresh operation nonce in its native generate tool command and identifies its exact source/store/session plus native current turn/message when exposed. Resolve the current interval from that executing command, rather than requiring the agent to reuse an assistant-message identity captured by an earlier inspection; OpenCode may create a new assistant message between commands. AgenticLens must match that command in authoritative source-owned records, its native tool call/part and latest eligible open interval. Treat explicit caller parameters as claims until source correlation passes. Bound source flush waiting and return caller-proof-unavailable when native records cannot correlate in time. No completed or earlier/resumed turn is accepted merely because its session ID matches.
3. For another session, provide an optional exact-owner read-only status adapter, enabled only for a known existing runtime endpoint with an inspected supported protocol. Its capability response must disclose whether it proves exact interval activity, session busy only, process alive only, idle/terminal, or unknown. Do not auto-start a daemon, enumerate unrelated sessions, resume a thread, send a prompt, request generation or infer endpoint credentials. If a family/version has no usable supported provider, return unsupported with a reason; this is a valid explicit result, not fake liveness. A provider interface alone must not be presented as working runtime integration.
4. The agent chooses among verified current-caller accrual, verified exact-interval runtime-status accrual, or preserve-supported-duration. The application independently validates evidence and decides eligibility within that operation. A typed option/input chooses the verification method and carries this executing command's nonce/identity where needed, not an unchecked caller-provided allow=true. A separate decision file or prior inspection is not mandatory. Mismatches, stale replies and invalid inputs produce explicit rejected decisions and leave the ledger intact. The agent may retry verification with a new observation; it cannot waive identity or freshness requirements.
5. Surface accepted verification basis, observation time, cutoff and limitations through the existing duration evidence/CLI JSON and human summary. Store only compact result provenance necessary to explain recorded duration, not credentials, private endpoints, raw transcripts or reusable local proof receipts. Existing dashboard coverage/cutoff presentation is reused; change visible labels only if needed to distinguish live-verified from unresolved/retained evidence. Ordinary API reads never perform liveness checks or advance cutoffs.

The practical initial implementation is current-caller proof plus a bounded read-only status-provider capability/result boundary and explicit unsupported fallback. A concrete native status provider is included only when local protocol inspection proves it can observe an existing exact owner without starting or mutating execution. This preserves useful behavior across all three source families even where cross-session querying is unavailable. If the user requires a working cross-session provider for every harness, that larger commitment needs a separately approved endpoint/version matrix; it is not supported by the present evidence.

## Typed observation and decision contract

Separate session identity from interval identity. The observation contains source, canonical operational store identity, exact native session ID, schema family/version, current turn ID or assistant-message/native call ID, native interval start, observed_at, evidence kind and result. Store paths are used to match a local lookup, not as a portable acceptance credential. Persisted history remains usable elsewhere without its source store.

Results distinguish active_exact_interval, busy_interval_unknown, process_alive_only, idle, terminal, unavailable, unsupported, stale, identity_mismatch and error. Only active_exact_interval or validated executing-caller evidence can authorize new provisional accrual of that exact supported interval. A current busy session may be executing a later turn, and a live daemon may own idle sessions. Missing/not-found source is unavailable, never proof of zero duration or retroactive death. Idle/terminal status observed now is not a historical completion timestamp; use a source-proven terminal boundary or preserve known cutoff with an explicit limitation.

Freshness is bound to one short-lived operation/challenge and exact native identity, with a documented finite deadline, response byte limit and bounded attempts. It is not an arbitrary source record age or PID-age threshold. No unlimited polling. Keep transport I/O and deadlines in adapters/CLI; pure domain eligibility consumes immutable evidence and explicit timestamps. Status/caller evidence is per owner/interval: a verified root does not verify its children, other roots or other harnesses.

A live command or status check proves activity at its observation boundary. Exact current native interval identity plus positive executing-caller or status evidence and no known terminal/replacement contradictions suffices for a provisional elapsed estimate from that interval's source start. Do not demand proof of uninterrupted execution or absence of hidden pauses: active duration is native interval elapsed, including tool waits, rather than CPU time. Reject a known stale or previous interval and known interruption/resume contradictions instead of backdating newly verified activity to an unrelated old start. Disclose that unrecorded pauses cannot be ruled out; this limitation alone does not block otherwise supported current-interval provisional accounting.

Check-to-snapshot race: resolve bounded evidence within the operation, choose the cutoff after the relevant verification and reconcile exact interval identity with source terminal/superseding boundaries. For self-verification, the matched native tool command is still executing while it acquires its own source snapshot; this can support a cutoff during that command without an additional handshake or an earlier observation-time cap. Reject a nonce found only in a completed/earlier command. For another session, a one-shot positive status response proves its observation boundary only: cap provisional accrual at the accepted observation time unless the supported protocol establishes activity through snapshot acquisition. Record observed_at separately from operation cutoff when they differ; do not extrapolate a positive reply into the later unchecked gap. A fresh source completion is measured from source; a changed turn invalidates earlier status correlation. Retry once within the budget or return unresolved. Later proof is not retroactive proof of an earlier historical cutoff. There is no claimed atomic transaction across daemon and SQLite/file sources.

Portability and retention: no liveness evidence is required to accept a valid stored ledger. Live checks enrich or authorize new observations only. If checking fails, do not erase an existing provisional contribution/cutoff or silently replace it with zero. Successfully extracted completed intervals remain authoritative and may replace provisional facts under the portable ledger contract. If the source is parse-complete but ongoing coverage cannot be re-established, merge only supported completed updates while explicitly retaining the previous supported unfinished subtotal/cutoff; do not treat the unresolved duration dimension as an authoritative empty replacement. Prevent overlap between retained provisional and newly completed intervals using source ownership/interval evidence; if mapping is ambiguous, preserve the old supported snapshot and report the blocked update. No union of successive cumulative duration totals.

## Alternatives and approval questions

Recommended: validated caller proof, optional read-only exact-interval status and explicit preserve/unknown fallback. This addresses the user's proposed split without claiming universal cross-session interrogation.

Alternative: explicitly accept source-open elapsed estimates with disclosed liveness uncertainty. This is simpler and already implemented in the pending candidate, but would leave stopped v1 open intervals advancing; it requires the user's explicit acceptance of that estimate policy.

Messaging a different agent is not a read-only poke. It can wake an idle session, create a new turn, trigger tool/model cost and alter the very state being measured. A reply proves the new activity, not that the previous unfinished interval was alive. Automatic messaging/resume and synthetic heartbeat prompts are excluded from this proposal. They would require separate authorization and still cannot establish historical continuity.

Approval must resolve whether current-caller verification plus explicit unsupported cross-session fallback is the acceptable minimum when exact native status is unavailable. No additional proof of uninterrupted execution is required for the agreed native-interval elapsed estimate. Exact CLI naming and bounded timeout defaults are routine implementation choices once these boundaries are approved.
