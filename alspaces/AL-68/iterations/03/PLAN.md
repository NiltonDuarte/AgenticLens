## Common wrapper and versioned native cache

The existing platform wrapper remains the implementation starting point; its supported installation becomes a stable user-level entrypoint on PATH, with no required wrapper or native executable inside adopting repositories. Resolve project configuration from the invocation context or explicit owning project, never from the wrapper installation directory. Every ordinary invocation resolves the explicitly owning project configuration, reads its exact AgenticLens version pin and detects OS/architecture from the environment executing the command. Do not select the native platform from the installing machine, a developer's host when executing inside a container, a branch, a ticket or a cached last-selected version. An explicit project argument may identify the configuration context for installed callbacks; it does not establish a session's project/ticket ownership. Continue validating authoritative source context before publication.

Proposed shared key: agenticlens.version in .agenticlens-config.yaml. This key is a new requirement, not implemented support. It must identify one exact supported release; missing, invalid, unsupported or ambiguous values are loud actionable errors. Do not silently substitute latest, another installed version, AGENTIC_LENS_VERSION or a global default. The shared version pin is authoritative. Machine-local YAML, environment variables and ordinary dispatch flags cannot override it; conflicting override attempts must produce an actionable configuration error. Local capture/source/path settings retain their existing precedence independently of version authority. Machine-local installation-root overrides are separate from telemetry.capture.state_dir and must not change session attribution, metrics destinations, database location or retention. The central native cache is proposed under ~/.agenticlens/bin/<version>/<platform>/ with the correct platform artifact in each leaf; moving binaries there does not authorize a permanent home capture database.

Repositories A and B may pin different versions on the same machine. Their selected native paths and installed files coexist; installing or changing A's pin must not replace B's files, change B's selected version, kill B's worker or rewrite B's hooks/configuration. Cache population is staged and validated before activation, handles concurrent installation safely and never exposes partially downloaded executables. A version/platform identity is immutable after successful installation; an explicit repair must preserve a recoverable prior artifact until validation succeeds. Use existing release-integrity and capture-protocol compatibility checks; no execution of a shell wrapper disguised as a native artifact or recursive self-dispatch.

The common wrapper has a dedicated bounded offline mode used by both agent lifecycle hooks and the optional Git hook. That mode performs deterministic configuration/platform resolution and executes only an already installed exact native artifact. It never downloads, probes latest, checks for updates, mutates the cache or invokes a package manager/network client. Ordinary CLI dispatch also requires the exact pinned artifact to be installed already: it must not download or install a missing version. Only explicit installation/update operations may populate the native cache. Hook invocation remains fully offline. A missing artifact must identify the required project/version/platform and explicit installation action without claiming capture or changing trust. Wrapper selection errors are actionable capture failures; the optional Git advisory retains its nonblocking policy while showing the failure clearly.

Replace obsolete instructions to bypass wrappers with this offline common-entrypoint requirement. Source hooks and the Git hook must carry their exact project/configuration context and use the same selection policy; they must not call the old updater behavior or freeze an arbitrary native filename during installation. After selection, an already-running native worker and its child publication processes retain that selected executable/version for the in-flight pass. They must not re-read a changed pin halfway through one pass or recursively invoke the wrapper. Future wrapper invocations observe the updated configured pin. Record the compatibility behavior at a version switch: installed hook/plugin templates, local capture protocol and configuration may differ from the newly selected release. Diagnose an incompatible installation and require an explicit setup refresh before claiming the new integration healthy; never silently rewrite templates, migrate trust or start updating in a callback. Existing worker/native processes may finish their accepted work; cross-version publication must retain the existing output locks and local-protocol safety checks rather than letting a pin change reinterpret state invisibly.

Bootstrap selection cannot depend on the selected native binary parsing the YAML that is required to select that binary. Specify and demonstrate a safe dependency-free bootstrap technique and supported pin syntax before implementing changed consumers. Do not introduce a mandatory Go, Node, Python or yq installation into adopting projects. Reject duplicated pin/section definitions, ambiguous YAML structures, unsupported value forms and unsafe version/path characters; never source/eval YAML or interpolate its values as executable shell text. Validate that comments, quoting and whitespace accepted by the documented pin syntax produce one consistent result across supported entrypoints. Unsupported syntax fails with an instruction to use the supported form instead of guessing. The bootstrap's supported syntax and restrictions must agree with the Go config loader/writer and generated examples.

Preserve the original argv boundaries, working/project context, stdin, JSON stdout, stderr diagnostics, exit status and signal behavior through dispatch. Lifecycle JSON output cannot be contaminated by banners, update notices or bootstrap chatter. POSIX dispatch should retain the selected native process's expected termination semantics. The present sh wrapper works in POSIX environments, including compatible Windows shells; the documented native PowerShell path currently bypasses it. Provide and verify a Windows-native entrypoint with equivalent configuration/version/platform/offline behavior without requiring an extra runtime or silently falling back to direct native invocation. The concrete bootstrap/entrypoint technique and any supported-platform limitation must be recorded and demonstrated before implementation adoption.

Explicit installation resolves the target project and exact pin, selects/downloads only that version's target platform artifact, verifies its identity/integrity and capture protocol, and installs or refreshes owned integration with preview/rollback. Initial setup without valid project version configuration must obtain or write an explicit selected pin as part of approved setup; it cannot bootstrap runtime by guessing latest. Existing AGENTIC_LENS_VERSION, latest-download, on-demand self-heal and background update-check behavior in both wrapper/downloader copies must be reconciled with exact pins. An explicit install/update operation cannot silently override the project's YAML, replace another pinned cache leaf or enable trust. Installation options must agree with the shared project pin; changing the pin is an explicit project configuration change, not an implicit effect of resolving or installing a binary. Local installation paths may vary while native version selection remains identical.

## Optional Git commit warning

Add a standalone bounded capture health check and an explicitly installed pre-commit integration that uses it. Setup may offer installation; it must not install it automatically or modify project CI, branch protection or global Git settings. Installation/removal/upgrade are additive, previewable and ownership-aware, preserve existing hook behavior and honor core.hooksPath. If safe composition is unavailable, stop that installation with actionable guidance rather than overwriting a project hook. A pre-existing hook's exit status remains its owner's behavior; AgenticLens's own default is advisory and must not block the commit.

At commit time, resolve the actual Git working tree/project from Git and configuration, then read only that exact project's local state and configured publication destinations. Shared hook directories must not capture the installing worktree's path as the runtime scope for every other worktree. Source-reported project/CWD metadata can establish that a session belongs to the same configured location; it cannot establish that the session authored the commit, contributed to its staged changes, owns a particular ticket or is the committing root. Canonical aliases and nested configurations follow iteration 02's ownership rules. Do not guess tickets from branches, staged filenames, role names or timestamps. This check observes capture health; it does not claim exact causal attribution to an upcoming Git commit or change iteration 02's committed-HEAD code-metrics definition.

Warn about evidence-backed missing bindings in that project, known bound contributors absent from an accepted publication, missing metric files for an observed bound collection, unresolved recorded child work, failed/stale extraction, publication failures and verifiable integration drift. Do not ticket-filter away unassigned rows: until binding, they cannot be attributed to a specific ticket. Conversely, do not warn about another directory's same-ticket session. Completely absent metrics can receive an actionable diagnostic when configured/observed collection makes that expectation concrete; there is no mandatory global session census or enforcement if users elect to accept absence during review.

The expected tail exemption requires a successfully published snapshot containing the exact committing session and evidence that only subsequent activity is outstanding. Use only a verified harness/session identity when available; project path, active state, process ID guess, role label or elapsed time does not prove it. An active bound root with zero published metrics still warns. A source refresh that failed or omitted data already available before publication still warns, including the existing stale-cache regression. Other unbound sessions in the same project still warn. Do not require a stopped root or a maximum tail-duration threshold. If committing-session identity or freshness ordering is unavailable, expose that limitation in diagnostics without falsely declaring a missing root, assigning another session as root or claiming everything is current. Missing caller identity alone must not trigger a commit warning. A generic pending/active flag after a successful snapshot is insufficient reason to warn; warnings require a concrete binding, missing-metrics, failed-refresh or publication problem. The native committing agent integration may supply already-authoritative context; do not invent a harness API for ordinary shell commits.

Group observed issues into one concise advisory per commit invocation, with detailed inspection available through status. Users can ignore the warning, disable the optional advisory through machine-local policy or remove the owned hook. Do not add a persistent per-issue acknowledgement subsystem in this iteration. Historical unassigned rows cannot be declared unrelated solely from age; preserve them for explicit resolution without silently binding or discarding them. The check itself is read-only. No hook should generate metrics, edit the index, stage files, commit, push, start an unbounded scan or wait for agents to stop.
