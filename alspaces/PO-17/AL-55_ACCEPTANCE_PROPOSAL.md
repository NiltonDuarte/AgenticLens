## Five choices and acceptance status

1. **Keep optional v4 arrays (recommended).** Existing Go models/DTOs and TypeScript contracts intentionally allow omitted skills/task_links. An empty read projection does not prove complete extraction. Accept existing absent/empty forms without normalizing every ledger or requiring a permanent migration marker. Alternative required arrays needs a separately justified compatibility design; none is justified by current consumers.

2. **Retain whole skill/task snapshots on incomplete OpenCode recovery, while refreshing successfully recovered session trees (accepted policy).** Skill/task rows lack a reliable session/source owner, so replacing or merging only a fresh subset can discard or duplicate historic facts. Preserve both old collections semantically unchanged until all required exact OpenCode owners and descendants can reconstruct their producer history. Do not infer row ownership from timestamps, role, turn numbers, or a task child link. Replace the whole collections only on complete successful recovery. When a previously known child is unavailable, retain that child and do not treat its root's nonempty result as complete; never replace a tree from a partial extraction that would drop it. Successful independent complete trees may refresh. Report both refreshed sessions and retained older collections explicitly in the per-ticket command result and command summary. Alternative: defer the entire OpenCode refresh until coverage is complete, retaining stronger snapshot consistency but delaying useful source refresh. A per-owner skill/task schema is a larger, currently unjustified option.

   Accepted limitation of the recommendation: session facts and ledger-level skill/task collections can represent different recovery times. No new persisted provenance/version label or frontend feature is proposed. CLI diagnostics communicate retention at recovery time; existing stored arrays remain usable, not newly certified fresh. If users require durable per-view freshness warnings, choose whole-source deferral or separately approve a provenance/UI contract. Ownerless collections with no reconstructible OpenCode owner history must be retained as unresolved, not emptied because there are zero eligible stored roots.

3. **Completion requires all owners of the applicable requirement (recommended).** Source selection authorizes refresh of that source; it does not redefine an existing global source_backfill obligation. On a ledger with pending source recovery, clear it only after every stored required root and descendant across its required sources has successful exact discovery, parsing, grouping, and validated recovery. One Codex success cannot discharge missing OpenCode or another Codex tree. Missing IDs, parse/grouping errors, and retained arrays receive explicit incomplete diagnostics; preserve unrelated pending steps. A successful selected-source refresh may leave global recovery pending. Already-complete canonical baseline data stays runtime eligible when an optional refresh fails and preserved data remains valid: report the failed refresh without inventing a new mandatory migration. Missing optional arrays alone never imply pending recovery. This distinguishes command refresh outcome from structural/runtime eligibility.

   Completion is bounded by known stored required owners and source discovery results; it cannot prove that unavailable historic sources contained no additional unknown sessions. Do not advertise exhaustive external history recovery. Unknown/ambiguous required owner attribution prevents a positive completion claim.

4. **Explicit recompute reaches and refreshes eligible sources without Force (recommended).** Canonical v4 with migration=nil must not silently skip explicit recompute. A successful complete source extraction refreshes its cumulative snapshots, including whole skills/task collections when choice 2 permits; an event-only update is not full recomputation. Ordinary runs retain routine skips. Force remains an explicit repeat control, never permission to erase unresolved facts, invent ownership, infer source equivalence, or enable heuristic fallback. Exact stored identity remains the default and heuristic discovery remains separately opt-in. CLI help must explain the final recompute/Force behavior consistently. Alternative: make Force mandatory for completed-ledger recompute and reject/explain an otherwise ineffective explicit request; this preserves the current broad help wording but is less consistent with explicit recompute intent and existing test naming. Never silently report success while skipping.

5. **Preserve current backup scope (recommended).** Standalone migrate supports backup/dry-run and atomic replacement. Backfill supports dry-run and temporary-file atomic replacement; it does not expose a backup option and its internal migrate request uses Backup:false. Do not describe these as the same guarantee. Retain both existing interfaces; no new backfill backup API in this slice. Atomic replacement prevents partial-write publication, not semantic corruption or rollback. If automatic rollback copies are required for every recompute, explicitly enlarge this scope rather than claim it is already delivered. Document manual backup as an operator option without implying migrate --backup necessarily copies an already-current ledger.
