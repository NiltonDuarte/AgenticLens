## Proposed engineering choices for approval

1. Keep current local capture/source key families and introduce shared `agenticlens.binary_dir`. Require an explicitly present boolean enable choice in the selected whole local file; preserve bounded numerical defaults. A shared-only capture policy no longer supplies required local settings. Error messages expose selected local origin without leaking private paths into shared ledgers.
2. Resolve base checkout through Git metadata, preserving nearer Git/config boundaries and physical path validation. Return a typed selected-config context including active shared root, local file and local origin for all readers. No probing inaccessible base fallback when a valid worktree-local policy already wins.
3. Use a stable installed native dispatcher for user callbacks and common CLI selection, with only platform-required launch glue. The initial installed native entrypoint must be capable of routing without project-bound arguments. Keep explicit installation separate from invocation; no network on selection. Final command and internal API names may follow the existing CLI idiom without changing these policies.
4. Interpret `binary_dir` as a directory containing the current host's AgenticLens executable, including the repository's normal `bin/agentic-lens` output on Unix and an explicitly documented Windows executable name. Validate format/platform and required native interface before selecting it; distinguish genuinely absent output from dangling/unreadable/invalid present output. Reuse cache-native filename conventions when available without requiring multi-platform artifacts for a single development build.
5. Retain an immutable executable artifact for each admitted worker build before mutable output can be replaced. Worker subprocesses execute that retained artifact; active/preferred identity is visible in status. Use existing worker and publication locks and avoid introducing a second supervisor. No automatic retention cleanup is added.
6. Keep current cadence/work bounds initially where compatible: refresh 15 seconds, debounce 500 ms, idle 120 seconds, max lifetime 30 minutes, pass timeout 30 seconds, 256 sessions and 64 MiB per pass. Keep backoff bounded by the selected lifetime/local budget and expose exhaustion; add a new numeric option only if the existing validated limits cannot express required behavior. Configuration errors do not consume a transient-error retry cycle.
7. Explicit migration recognizes only provably unchanged owned project/home callbacks. Unknown or modified Python workarounds are diagnosed for explicit handling; no filename-only deletion. Preserve trust and pending state. Do not claim absence of duplicate callbacks until native inspection verifies it.

These are implementation details within PO-20's approved policies. If native routing/trust interfaces cannot deliver the stated outcome or a choice changes user-visible policy, stop and return to the parent/planner for a material scope decision; do not weaken acceptance.
