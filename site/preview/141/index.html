01 / Understand team telemetry

How does your team work with agents?

Follow skill use, agent and role activity, model choices and context window saturation. Bring the activity of planners, coders, testers and reviewers into the same project view.

Explore: which skills are used, how work passes between roles, where tokens are spent, and which sessions need a closer look at context pressure.

From sessions to understanding

Skills. Roles. Models. Context.

  • Skill invocations and delegation activity
  • Agent roles and model usage
  • Token use, cache use and context growth
  • Recorded activity across tickets

02 / Track evolution & compare tickets

Are changes helping your development cycle?

Follow lines of code, recorded cost, token use and cache use as the project grows. Compare tickets by elapsed and active time, token spend and developer steering to explore how development changes over time.

Ask: after a change to AGENTS.md, skills, guidance or specifications, do comparable tickets need less steering, time or tokens? Use the charts to investigate; account for task difficulty and missing data before attributing a change to your guidance.

03 / Share the project record

Keep team history where the project lives.

Commit the telemetry ledger with the code. Git provides a natural shared history, so teammates, team leads and engineering managers can see how the project and its development practices evolve across machines and harnesses.

Review together: inspect ticket summaries and project charts, compare the work over time, and choose the next improvement from a shared record. Private session stores stay local; original sources are still needed to recover missing trace detail.

Context diagnostics when you need them.

Anomaly detection can help identify context pressure, repeated tool failures and other patterns worth inspecting. Follow the underlying evidence before deciding what to change. Read the diagnostic rules.

i

Evidence has limits. Keep them visible.

Comparisons support investigation, not a causal verdict on a skill or instruction change. Task scope, model choice and missing evidence can affect the picture. A token count alone does not explain why a ticket was difficult.

Observed cost is a reported amount, including a reported zero. Partial cost is a known subtotal with missing contributions. Unavailable cost is unknown, not zero. Current Codex extraction does not establish USD cost. These are not verified invoice amounts or promised savings. Read cost semantics.

AgenticLens observes the work.

It is not an agent executor or orchestrator, a coding assistant, a hosted monitoring service, or proof of code quality. Your harness runs the agents. You interpret the evidence.

A small, local architecture

Your machine.
Your project history.

Local harness stores and Git provide inputs. Adapters read them; pure analysis derives the recorded metrics. Durable ledgers retain project facts for the CLI and the local embedded dashboard.

Local sources are authoritative when successfully refreshed. Unavailable sessions remain preserved in supported shared ledgers, across developers, machines and harnesses. Optional source detail enriches the record when available.

The native agentic-lens manager installs and selects the project’s pinned engine. The separate agentic-lens-engine performs telemetry work and embeds the dashboard. The installed application needs no production Node runtime.
