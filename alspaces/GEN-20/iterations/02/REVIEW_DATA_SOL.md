## Findings

### DATA-SOL-1: Ordinary configured bases beneath a directory named worktrees are rejected

- Severity: 5/10. Classification: introduced correctness regression; blocking supported path resolution. No data loss demonstrated.
- Location: backend/internal/adapters/capture/project.go:382-386, consumed at project.go:93-94 and 104-105.
- Trigger: select an ordinary state base such as `/tmp/example/worktrees/capture-state`, with a valid project configuration and no existing registry. The final component is a valid coordinate token, so the broadened isCoordinationPath treats the base as an already allocated coordination path.
- Expected: resolve the configured base to `<base>/projects/<project_name>` and allow no-write provisional preview followed by allocation. A basename alone does not establish a persisted worktree mapping or the complete coordination namespace shape.
- Actual/consequence: resolveCoordinationNamespace interprets `/tmp/example` as the registry, then fails namespace containment/shape validation with `capture namespace alias must preserve projects/<configured-project-name>; configure the intended base explicitly`. The user already selected the intended base. Preview and writable/read-only project opens share this resolver, so installation and capture cannot use this otherwise valid configured storage location. The baseline numeric-only classifier did not misclassify `capture-state`.
- Evidence: isolated Go overlay probe TestReviewDataConfiguredBaseUnderWorktrees, using sharedWorktrees only to create temporary fixture repositories, ran the actual PreviewStateLocation and reproduced the error. Command from backend: `go test -overlay /tmp/gen20-data-review-9wjt66yh/overlay.json ./internal/adapters/capture -run '^TestReviewDataConfiguredBaseUnderWorktrees$' -count=1 -v`; FAIL at the expected acceptance assertion, exit 1. No shared source/test file was edited.
- Refuting guards checked: lexical and physical path branches both use the same broad classifier before ordinary base resolution; registry ownership validation does not recover this case. The complete `projects/<name>/worktrees/<token>` shape and persisted mapping guards correctly reject unknown coordinates, but are reached after a valid base is already misclassified.
- Required correction: distinguish an ordinary configured base from a coordinate namespace using sufficient namespace context, while retaining rejection of unknown/foreign tokens and escaping aliases within actual coordinate namespaces. Add an isolated ordinary-base regression assertion; do not weaken containment or adopt unknown coordinates.
