# AL-84: Support flexible workspace layouts and adopt OpenSpec

Execution: [AL-84 OpenSpec change](../../../openspec/changes/al-84-flexible-workspace-layouts-and-openspec/README.md). Approved iteration: 01.

## Goal

Let users organize ledger-backed tickets in any explicitly configured workspace directories through one lean platform capability. Use that capability to deliver the repository’s complete OpenSpec workflow, with execution planning, evidence and telemetry in the same change home before and after archive, while roadmap tickets remain separate.

## Context

The [PO-24 assessment](../../PO-24/ASSESSMENT.md) confirmed that configuration can discover ledgers inside OpenSpec changes, but detail readers and publishers reconstruct a direct path from the ticket ID. Multiple roots alone cannot follow archive renames or prevent active-folder recreation. Users also need ordinary layouts such as `alspaces/archive`, `alspaces/al`, `alspaces/al2`, `alspaces/po`, `alspaces/fix` and documentation folders, alone or together with an OpenSpec tree. These directories are equal first-class workspaces, not compatibility roots or OpenSpec-specific modes. Repository agents, skills and backlog still assume a single ticket root. This ticket delivers the complete adoption outcome in one slice, as explicitly requested by the user; platform support without the repository/guidance cutover is incomplete.

## AgenticLens boundary

AgenticLens is concerned only with directories containing an `agentic_metrics.json` ledger. A directory without a ledger is outside its workspace model: AgenticLens does not discover, list, register, bind, track or represent it in the dashboard. OpenSpec and ordinary repository workflows own planning-only folders. First generation receives an explicit canonical ticket ID and output destination and writes the ledger there; the ledger then supplies recorded identity for all subsequent operations. This clarification supersedes earlier wording about ledger-free workspace binding or recognition. It does not remove source/session capture or exact session ownership requirements.

## Roadmap and execution boundary

Tickets are the long-term project roadmap: requested outcomes, prioritization, readiness and dependencies may evolve. Keep existing roadmap ticket documents and their index separate from OpenSpec. When a ticket is selected for work, create a linked OpenSpec change as its execution workspace, holding approved scope, technical design, tasks and delivery evidence. Ticket and change link to one another; later ticket edits do not silently change approved implementation scope. Change archive or checkbox completion does not by itself complete the roadmap ticket. This supersedes the earlier requirement to migrate every active roadmap specification into OpenSpec changes.

## Acceptance criteria

- Support one or many explicit user-selected workspace directories through the same configuration, ledger discovery and location-resolution model. Use only `workspaces.roots`, including a one-entry list for a single directory. Retire `workspaces.dir` without backward compatibility; users and this repository must explicitly update. Reject old configuration fields, remove old single-directory runtime CLI/API aliases and update their callers; do not introduce fallback parsers or automatic shape conversion. Folder names, grouping, depth and ticket-prefix/type associations are user decisions: no reserved alspaces/OpenSpec paths, obligatory layout or inferred routing. Missing, invalid or contradictory policy fails clearly rather than selecting an invented root.
- Accept configured roots at arbitrary depths with explicit bounded discovery scope sufficient for direct and nested layouts. Each directory entry contains its path and its own explicit maximum depth and directory budget, without a separate root ID or minimum-depth setting. Configuration writers emit `max_depth: 0` (the selected directory itself only) and `max_directories: 300` per entry; runtime reads that policy rather than applying hidden defaults. Greater traversal depth requires explicit configuration. This repository selects `max_depth: 1` and `max_directories: 300` for `alspaces`, `openspec/changes` and `openspec/changes/archive`, because their ledgers live in immediate ticket subdirectories; root-only writer initialization must not replace that explicit selection. Enumerating immediate children is available where the user selects container roots; do not force shallow discovery on every workflow. Demonstrate plain alspaces, its archive, prefix/type-grouped folders, arbitrary renamed folders, OpenSpec changes/archive and a mixture of them in one selected project. No code changes or special fallback mode are needed when the user reorganizes those configured paths.
- All workspace consumers use one stable-identity/location resolution contract: listing, detail, configured artifacts, events/traces, comparison, live workspace selection, manual default destination selection and automatic publication. Moving a known workspace between configured roots preserves its identity, supported facts and ordinary access.
- Create OpenSpec changes from explicit configured canonical ticket IDs plus descriptions, for example canonical `AL-123` with folder `al-123-add-login`. Preserve canonical spelling separately from mutable folder names. OpenSpec already accepts this lowercase naming convention; use supported setup/creation extension points rather than requiring an upstream fork or an unverified hook. The OpenSpec creation workflow rejects invalid names/prefixes and collisions without overwriting content. First ledger generation records the supplied canonical ticket ID; subsequent directory renames do not change it or require folder-name inference.
- Existing valid ledgers supply canonical ticket identity regardless of directory name. Discover only ledger-backed workspaces. First generation uses an explicit canonical ticket ID and output destination; do not introduce prior folder recognition, workspace registration, persistent directory-binding configuration, marker files, UUIDs or separate workspace bind/create/resolve CLI commands. Multiple distinct ledgers for one ticket require explicit destination selection through existing generation/read interfaces, not first-root precedence, automatic merging or preference for an active-looking folder.
- Physical aliases/overlapping roots cannot enumerate one directory twice. Containers, nested spec folders and planning-only changes without ledgers are not AgenticLens workspaces. Discovery follows the selected scope and recorded ledger identity. Folder labels such as archive, docs or fix do not establish completion dates, ticket type or write policy. An unavailable root produces partial-result diagnostics while valid sibling roots remain usable. Expose location/conflict/recovery context consistently in CLI, API and dashboard; missing or unavailable source/enrichment facts for an existing ledger remain unavailable, not measured zero. A folder without a ledger has no AgenticLens listing or placeholder.
- Refresh of an existing ledger resolves its actual directory across configured roots. If that target disappears or moves concurrently, report/retry resolution without recreating its old directory. Explicit output paths must agree with the selected recorded ticket identity and containment policy. First ledger generation requires an explicit destination; never invent a root or infer prefix routing from directory names. Do not introduce automatic workspace creation routes. OpenSpec or ordinary filesystem workflows own folder creation; AgenticLens publishes telemetry through its generation interfaces.
- Moving a workspace into a user-selected archive directory changes no lifecycle facts by itself. Refresh its existing ledger without creating a sibling at the former location; for an OpenSpec-archived change, refresh must not reactivate the change. Concurrent archive/move and interrupted current-format publication must yield one valid update or an explicit recoverable retry, with no lost history, duplicate outputs or recreated parents. Verification must exercise real filesystem movement rather than only compare path strings. Do not add legacy publication-journal adapters; unsupported pending journals stop safely with explicit recovery/upgrade instructions and preserve pending files. Existing older ledger schemas use the established explicit migration workflow; this ticket adds no compatibility reader or automatic conversion. Current-format portable historical facts remain supported.
- Store publication journals and locks in a writable machine-local AgenticLens state home, separate from versioned binaries and capture-registry storage. Setup writes local `agenticlens.state_dir` explicitly, initially `~/.agenticlens/state`; writers may initialize it without capture installation or enablement. A small adjacent transient pending-publication indicator moves/copies with the ledger, allowing readers without the private journal to report incomplete publication. It is transaction status, not a workspace identity sidecar. Read-only operations and completed portable ledgers remain independent of private state; unavailable recovery data must not hide pending state or authorize partial history as accepted. Verify durable transaction ordering, crash/retry, unavailable state-home writes, copied interrupted sets and originating-machine recovery.
- Keep exact source/session bindings attached to the canonical ticket within the existing project/worktree boundaries, independent of the selected root. Folder moves need no rebinding; multiple roots do not permit ownership reassignment across worktrees. Preserve unavailable/partial owners, other contributors/harnesses and legitimate multiplicity; complete local refresh remains authoritative and repeated refresh remains idempotent.
- Extend setup/operator workflows to configure and explain user-selected roots, ledger discovery scope, explicit first-generation destinations and ledger-based resolution after moves without prescribing directory names. Add a supported, verified and pinned OpenSpec setup that uses these same core capabilities. Configure its selected changes/archive roots and standard proposal/design/tasks paths in place, without a separate per-ticket AgenticLens workspace. Preserve unrelated/custom instructions, skills and configuration; retain existing setup confirmation requirements and distinguish shared policy from local source/capture state.
- Demonstrate source-backed Codex/OpenCode telemetry in the created change with explicit conventional type, exact ownership and honest missing-source/cost behavior. OpenSpec's other assistant integrations must not be advertised as new AgenticLens source adapters. Record the tested CLI/schema release; unknown fields and advisory naming rules cannot be presented as enforced behavior.
- Reconcile AGENTS.md, relevant technical/regression rules, shared personas/references, Codex registrations, applicable OpenCode setup, every affected AgenticLens skill/template, and setup/operator/contributor documentation. Search active sources for conflicting path/lifecycle rules and correct the owning source; preserve unrelated historical audits.
- Use one authoritative OpenSpec change home for selected execution scope, technical design, tasks, delivery/review evidence and telemetry. Keep the roadmap ticket and roadmap index separate, with clear ownership of evolving intent and priority/dependency/status information; do not duplicate the entire roadmap inside OpenSpec or keep parallel editable execution contracts/plans. Preserve planning-only PO sessions, approval before coding, specialist role boundaries, model/review attribution, required verification, final telemetry and PR handoff. Planning readiness, checkbox completion, approved scope, change archive and verified ticket delivery remain distinct.
- Cut over the live AgenticLens repository to the verified OpenSpec structure/schema and multi-root configuration. PO maintains roadmap tickets independently. When a PO/GEN/development ticket is selected for execution work, that work uses a linked ticket-prefixed OpenSpec change home; backlog entry creation alone does not require a change. Keep the repository’s chosen alspaces directories as ordinary configured roots alongside its selected OpenSpec roots, with appropriate discovery scopes. This repository chooses OpenSpec for future work; the platform continues to support actively creating and using alspaces or any other configured layout without deprecation or a compatibility label.
- Retain roadmap specifications and `alspaces/plan/TICKETS.md` in their existing structure, preserving ticket IDs, requested outcomes, prioritization, readiness/dependencies and active-owner boundaries. Link tickets to execution changes when work begins, and link each change back to its ticket. Do not migrate pending tickets into changes, replace the roadmap with `openspec/backlog.yaml` or require a generated backlog view. Update contributor entrypoints to explain both roles; preserve historical navigation and facts.
- Review the configuration, guidance and execution artifacts actually affected by OpenSpec adoption, coordinate owners before moving writable files, and provide a recoverable adoption sequence using Git-tracked changes, verification and documented rollback. No wholesale roadmap migration or separate repository-migration framework is required. Failure preserves the prior supported configuration/history and exposes partial progress. Do not duplicate ledgers, silently reticket sessions, rewrite completed audits or depend on original session stores/private capture receipts for historical reads.
- Demonstrate the complete selected workflow: planning, scope change, explicit implementation approval, native source capture/publication, dashboard/CLI detail, retained incomplete-review evidence, completion, OpenSpec archive and late refresh. Include copied-history reads without original sources, movement between arbitrary configured roots and first ledger generation in a user-selected grouped folder. Verify that ledger-free folders remain absent from AgenticLens before generation, become visible after generation, and require no registration. Confirm OpenSpec works through the same ledger discovery/read/publish path and no writer recreates a prior location. Text searches or synthetic fixtures alone do not establish native runtime compatibility.

## Implementation notes

[PO-24 SPEC.md](../../PO-24/SPEC.md) owns the initiative context; this ticket owns implementation acceptance. This is one delivery slice, not a set of independently completable sub-tickets. Concrete configuration syntax, discovery bounds, resolver contracts and supported custom-schema design belong to the developer contract. The root collection and identity/location resolution are generic platform capabilities; OpenSpec integration supplies workflow/naming/artifact guidance instead of a second scanner or publisher. AgenticLens does not implement a planning inventory. The separate roadmap remains repository workflow; OpenSpec changes hold execution work and require a ledger before AgenticLens discovers them. Preserve the [portable ledger contract](../../../TECHNICAL_GUIDELINES.md#portable-ledger-contract) and relevant [regression boundaries](../../../docs/REGRESSION_PREVENTION.md).

AL2-2 retains ownership of compressed archive packages and their precedence rules; OpenSpec archive folders need no package archiver. AL-81 independently separates manual generation from capture-registry access; do not reintroduce that dependency or weaken automatic ownership. Coordinate shared worktree/capture paths with AL-80 without taking its scope. Cross-repo OpenSpec stores, additional harness adapters, dynamic capability/spec-glob browsing and phase/progress analytics are not required for this adoption slice.
