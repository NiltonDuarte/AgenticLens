## Iteration 02 — One-time setup for Codex binding

The user requested one-time setup so a fresh workspace-write agent can bind its ticket without a per-run directory flag. At `a6a115f7`, a grant for the capture directory worked, but it also allowed sandboxed writes to the worker's retained executables. The coordinator rolled back that grant. The user approved a dedicated binding inbox for the installer and worker. The earlier audit evidence applies to its recorded revision.

The Codex user installer owns a dedicated inbox under the effective Codex home. Grant workspace-write access to that directory only. Preserve other user grants, sandbox mode and hook trust. Include directory/configuration changes in preview, installation, migration and recovery, and remove only provably installer-owned permissions at uninstall. Protect the user configuration from concurrent edits and fail closed on conflicting file types or path aliases. OpenCode and existing direct operator commands retain their supported behavior.

The native hook supplies exact source and request context. The sandboxed submission command uses that context to derive a response slot and authenticate the canonical response fields. Use separate derivations for slot naming and response authentication. Neither the slot name nor the envelope contains a reusable bearer challenge. Authenticate the complete ticket ID, title and type and bind them to the expected worktree, native session and request. The worker checks only expected slots for its own known registrations under bounded session, byte and time budgets. It verifies source ownership and current binding state before committing private metadata and scheduling publication. Retry incomplete source verification, preserve prior facts and make repeated accepted submissions idempotent. Treat the inbox as untrusted filesystem input. Handle file type, replacement and symlink hazards without following arbitrary paths, blocking on special files or deleting unrelated entries. The inbox authenticates submitted content against the native request. OS-level confidentiality between processes that already share read access to private source or registry storage is a separate boundary.

The installation coder owns setup, permission editing and migration. The runtime coder owns authenticated submission, callback feedback and worker consumption. The tester owns independent cases for fresh-root binding, edited/replayed records, unsafe file types, preservation of other sessions, restart and installation rollback. The coordinator owns the real settings, integration, review and delivery.
