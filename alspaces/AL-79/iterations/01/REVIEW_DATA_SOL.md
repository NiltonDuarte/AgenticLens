## Findings

### DATA-SOL-01: Automatic bound collection inherits shared capture budgets

- Severity **6/10**; classification: introduced required-contract defect.
- Expectation: automatic capture uses one selected whole local policy; omitted numeric settings use documented defaults. Shared capture keys must not supply those values. Manual compatibility must not change the automatic collector's policy.
- Trigger: shared YAML retains `telemetry.capture.max_source_bytes: 1`; complete selected local YAML explicitly enables capture and sets state/source but omits that numeric option. This is a supported transition from old shared settings, with a valid local policy.
- Locations: `backend/internal/adapters/config/capture.go:55` and `:65`; `backend/cmd/agentic-lens/main.go:97`; `backend/cmd/agentic-lens/capture.go:505`; caller `backend/cmd/agentic-lens/capture_worker.go:203`.
- Trace: worker admission uses ResolveCapture, which starts from defaults and returns 67,108,864 bytes. Its bound publication child runs generate --capture-auto. Both runGenerate and reconcileCaptureGenerationAt instead use ResolveGenerationCapture, which decodes shared settings and overlays local settings on them. The latter passes the inherited one-byte limit directly to Store.ReconcileAt. The automatic-enabled guard validates the strict local policy but does not replace these collection limits.
- Consequence: valid, complete local source updates cannot refresh bound facts; automatic generation can still exit successfully publishing older baseline data. A local setting with a documented default does not control the actual bound collector.
- Raw probe evidence: `TestAL79DataAutomaticSnapshotPolicyIgnoresSharedCapture` logged `worker_bytes=67108864 publication_collection_bytes=1` and failed its equality assertion. The actual CLI probe `TestAL79DataSharedBudgetBlocksAutomaticBoundRefresh` first generated root input 10, rewrote the complete source to 31, added only the shared one-byte limit, then ran generate --capture-auto. It exited successfully and read back `owner=root input_after_complete_source_update=10`; the expected 31 assertion failed. CLI probe duration 0.21s, package 0.898s.
- Required disposition: keep legacy manual compatibility where required, while routing automatic publication and its reconciliation through the strict selected policy. Add a regression through the bound automatic collector, rather than only testing ResolveCapture.

### DATA-SOL-02: Root-journal recovery writes a home before acquiring its lock

- Severity **6/10**; classification: introduced atomicity/concurrency defect.
- Expectation: installation/recovery modifying shared root and home artifacts holds the locks for those resources. Interrupted installation must not overwrite another installer while claiming exclusive transaction ownership.
- Trigger: an interrupted root-owned journal includes writes to a Codex home's hooks/receipt; another installer already owns that home's real kernel installation lock. Different configured install roots can share one Codex home. A later invocation tries to recover the first root.
- Locations: `backend/internal/adapters/capture/user_install.go:79`, `:86`; `backend/internal/adapters/capture/user_install_transaction.go:32` and `:43`.
- Trace: InstallUserCodex acquires the selected root lock, immediately calls recoverUserInstallation(root), and only afterward attempts acquireInstallLock(home). Root journals contain home paths. rollbackUserJournal reads/checks/restores those paths without acquiring their home locks. The later busy check cannot undo the unauthorized overlap.
- Raw probe evidence: `TestAL79DataRecoveryHonorsHomeLock` acquired acquireInstallLock(home), created a minimal valid interrupted root journal with hooks before/after bytes, and invoked InstallUserCodex. It returned `capture installation is already in progress; retry after its owner finishes`, but hooks changed from `{"hooks":{"Stop":[]}}` to `{"hooks":{}}` while the lock remained held. The assertion failed in 0.01s. The journal is a deterministic crash-state fixture, not a live-user-file mutation.
- Consequence: recovery can modify hooks/ownership concurrently with an installer that legitimately owns the home. The byte comparison is insufficient: after recovery checks transaction-owned bytes, the lock owner can publish its update, then recovery can overwrite it with the old before-image. The probe establishes lock bypass; that read/check/write interleaving establishes the lost-update risk. It does not claim a live lost-update incident occurred.
- Required disposition: acquire the ownership locks for all resources referenced by recovery before restoring their bytes, including a journal's previous home if the current invocation selects another home. Do not assume the current target home is the only home in an interrupted root transaction.

### DATA-SOL-03: An explicitly bound child blocks its parent's reconciliation

- Severity **6/10**; classification: pre-existing dependency defect conflicting with AL-79 acceptance, not introduced source regression. children.go is unchanged in C2, but the new native callback and automatic worker use it.
- Expectation: source-proven same-task children inherit a bound parent unless explicitly bound already. An explicit child assignment remains authoritative; parent recovery must not force it into another ticket or prevent the unrelated parent ticket from publishing.
- Trigger: root explicitly bound TEST-100; native child with source-proven parent linkage explicitly bound TEST-200; SubagentStart/Stop supplies its child transcript, producing normal pending child recovery.
- Locations: `backend/internal/adapters/capture/children.go:131`, `:299`; `backend/internal/adapters/capture/reconcile.go:136`; `backend/cmd/agentic-lens/main.go:342`.
- Trace: inheritChild unconditionally calls CaptureBinding(existing child ticket, empty requested, parent ticket). CaptureBinding correctly refuses reassignment, but recoverChildren treats that refusal as failure of the entire parent reconciliation and leaves the queued child in place. Automatic generate exits before publication. The fixed-point inheritance code also labels differing explicit parent/child tickets as failure rather than treating the explicit child as an exception.
- Raw probe evidence: `TestAL79DataExplicitChildTicket` used real SQLite Store registration, exact rollout files and source-proven ancestry. Reconcile(TEST-100) returned `session already bound to TEST-200; refusing conflicting ticket TEST-100`, `parent_sessions=0`; List still showed child TEST-200/explicit_agent_response/pending and parent TEST-100/explicit_agent_response/current. The expected successful parent reconciliation failed. This repeats until the queue is changed; facts and explicit assignment were preserved, so no data erasure is alleged.
- Required disposition: preserve explicit child binding and settle/skip its inheritance work without aborting the parent ticket. Verify both tickets can continue collecting and publishing with exact source parent linkage retained.
