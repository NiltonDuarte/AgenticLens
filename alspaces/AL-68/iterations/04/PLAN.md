## Grounded implementation seams

- Configuration: config/loader.go currently decodes capture policy with DefaultCaptureConfig and validates LoadFromFile before Load overlays local settings. config/capture.go ResolveCapture also starts with defaults and validates after its CLI override. Both can conceal an omitted path. config/writer.go GenerateConfigYAML replaces the whole capture policy when StateDir is empty; the new write-time insertion must preserve other configured fields. These paths are under backend/internal/adapters/.
- Storage: capture/project.go ProjectState hashes the physical project directory; OpenProject claims a singleton project_owner. capture/store.go keys registrations by source/store/session identity. These assumptions must change before separate worktrees can safely open one configured-name database.
- Scheduling and publication: capture/worker.go stores singleton request/acknowledgement and ticket cursor records, and uses one worker.lock/status/log directory. Diagnostic heads, installation manifests, disabled state, publication locks/journals and CLI project/state checks also depend on the existing directory boundary. A path substitution alone is insufficient.
- Creation/update: GenerateDefaultYAMLForVersion, GenerateConfigYAML, CLI init and guarded scaffold completion, and the POSIX/PowerShell setup downloaders write capture configuration. Downloaders currently emit a pin-only scaffold with a project-local state path. There is no established general surgical configuration-update command; design that explicit update responsibility rather than documenting an invented command or using init --force as repair.

## Requirements

### R4-01: write the default; require the configured value

Creation must write telemetry.capture.state_dir as ~/.agenticlens/state. This portable home-relative value resolves using the executing user's home, including native Windows, without shell evaluation or new runtime dependencies. The resulting normal database path is ~/.agenticlens/state/projects/<configured-project-name>/registry.db; for project_name AgenticLens, the final segment is projects/AgenticLens/registry.db.

An explicitly requested configuration update inserts this default only when the key is absent. Preserve an existing explicit shared path, machine-local override and unrelated capture fields. An empty, null or invalid existing value requires a visible correction; do not silently replace it. Changing an existing path to the home layout is an explicit migration, not incidental formatting or default insertion. As an iteration04 implementation deliverable, deliberately update this repository's shared .agenticlens-config.yaml and canonical generated/setup examples to the home policy, migrating its existing capture state under R4-03. This ticket-specific cutover is separate from the generic updater, which preserves users' explicit paths, including project-local values that resemble the previous default.

Operational configuration reads must require a present, nonblank, valid string after field-wise shared/local overlay. A valid local-only explicit value can satisfy the requirement; an omitted local value preserves shared configuration. Missing, empty, null and wrong-type effective values fail with a diagnostic naming telemetry.capture.state_dir and the configuration to repair. A CLI state override cannot rescue invalid configuration; apply permitted overrides only after validating configured presence. Remove state-path fallback from full loaders, capture resolution and their operational callers; unrelated numeric capture defaults need not be removed.

The requirement concerns the configuration key, not a pre-existing filesystem directory. Reading valid configuration must not create the home directory/database, migrate data or write configuration. Resolving ~ in an explicitly configured value is path expansion, not fallback. Relative explicit paths remain relative to the owning configuration root, independent of hook cwd. An unavailable home for a home-relative value fails visibly.

Explicit creation/update tooling may inspect incomplete raw configuration to repair it, but must not expose that as a valid operational configuration or launch capture before validation succeeds. Keep binary/bootstrap readiness distinct from complete configuration. New pin-only scaffolds must contain the state path, remain incomplete without configured project_name, and require guarded completion before capture. Audit the common wrapper, native CLI and both installer paths so none bypasses the required key or silently supplies a runtime path.

### R4-02: configured-name storage with exact-worktree scope

Use required project_name as the logical project identity and home namespace. Do not substitute a checkout path/hash, branch or inferred repository name. Define a portable, collision-free representation for names that cannot safely be literal path segments; retain the exact configured name in metadata. Reject traversal, reserved/ambiguous names or filesystem collisions visibly rather than applying a lossy slug that merges distinct names. Never let configuration escape the selected state base.

Worktrees with the same configured name share the logical database while retaining explicit physical-worktree scope for registrations, bindings, source snapshots, diagnostic heads/history, installation provenance and publication work. Audit every query and uniqueness constraint, not just the database opener. A duplicate name in unrelated repositories must not merge metrics or authorize cross-directory reads/publication. Different names remain separate. A project rename selects a different namespace and requires explicit state migration; no implicit aliasing occurs.

Replace the singleton ownership assumption with validated project/name and exact-worktree ownership records. Scope requests, acknowledgements, cursors, disablement, worker status and associated coordination files so one worktree cannot acknowledge, starve, disable, overwrite or publish another's work. Preserve lock-before-read, exact destination validation, journal recovery and failed-work retention. Coordination within a shared database must remain bounded; no global source census is added. Name-based grouping does not relax source store/session identity checks or the prohibition on guessed binding.

### R4-03: explicit relocation and recovery

Design a reviewed, dry-run-capable migration/update operation, with its final interface proposed before implementation. It must handle existing project-local and externally configured state, retain verified physical ownership, and preserve bindings/challenges, pending generations, accepted snapshots, diagnostics, cursors, installation ownership and recoverable publication journals. Do not merely copy a live SQLite main file while WAL writers remain active.

Coordinate or stop only the affected owned workers before cutover; fence concurrent callbacks and older native writers so acknowledged work cannot disappear between locations. Refresh owned hook/state references explicitly and preserve edited/foreign integrations. Validate the destination and its existing contents before merging or replacing anything. Ambiguous or conflicting state fails visibly with the old state preserved. Stage changes with recoverable rollback; do not delete the original state until successful validation and an explicit cleanup decision. Version local-state compatibility deliberately; older binaries must not silently open incompatible state. Ledger schema v5 remains unchanged.

Home storage must survive worktree deletion, retaining diagnostics and pending work. This does not prove final extraction, preserve missing raw sources or authorize publication to a deleted/recreated checkout. Diagnose unavailable source/destination or changed ownership, retain pending evidence, and require explicit recovery into a verified destination. No background recreation of a deleted worktree, rebinding by name or destructive automatic retention is included. No cleanup command or retention duration is introduced by this iteration.
