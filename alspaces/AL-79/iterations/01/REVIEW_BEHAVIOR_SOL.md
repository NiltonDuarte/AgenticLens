## Findings

### BEH-01: User installation permits undisclosed duplicate project callbacks

- Severity: **6/10**. Classification: **introduced required-contract defect**.
- Locations: `backend/cmd/agentic-lens/capture.go:136`, `backend/internal/adapters/capture/user_install.go:153`, `backend/internal/adapters/capture/user_install.go:203`.
- Supported expectation: PO-20 F2 and AL-79 native installation acceptance require explicit safe legacy transition, making conflicting duplicate invocation visible and resolving verified owned duplicates explicitly. Existing project callbacks must be preserved until migration is explicitly selected; silently activating another set does not satisfy that boundary.
- Trigger: a repository already has a valid active owned Codex project installation. Run the recommended `capture install-user --repo PROJECT` without `--migrate-legacy-repo`.
- Consequence: installation succeeds with an ordinary success result while leaving both the old project callbacks and new user callbacks active. Native discovery can invoke both integration sets for the same event. Old callbacks retain their frozen project/source/state arguments, so this can produce redundant handoffs and competing or stale binding/routing behavior. The probe does not claim that ledger totals necessarily double; snapshot identity still provides independent deduplication protection.
- Trace: the CLI has the selected project but passes only `LegacyRepository` from the optional explicit flag. `InstallUserCodex` checks conflicting markers only in the user hook file. It does not inspect the current/base project's active legacy installation when the migration flag is absent. The guarded removal path exists and works when explicitly requested.
- Reproduction: disposable overlay `TestBehaviorProbeLegacyUserDuplicate` invokes the actual existing project installer, then actual `install-user`. Both return success; project hook bytes remain identical, old project SessionStart group count is one and new user SessionStart count is one. The success output contains no duplicate diagnostic. Positive control repeats `install-user --migrate-legacy-repo PROJECT`; the old group is removed. The probe neither edits product files nor fabricates an installation receipt.
- Required correction: diagnose/reject conflicting existing project activation before completing user installation unless explicit migration resolves it, including the Git-resolved base when invoked from a linked worktree. Preserve unknown/modified groups and pending state. Do not silently remove legacy hooks.

### BEH-02: Legacy disable no longer stops a running automatic publisher

- Severity: **7/10**. Classification: **introduced behavioral regression**.
- Locations: `backend/cmd/agentic-lens/capture_worker.go:334`, `backend/cmd/agentic-lens/capture_worker_fence.go:45`; affected unchanged disable entry point `backend/cmd/agentic-lens/capture.go:220`.
- Supported expectation: the retained `capture disable`/`capture uninstall` commands deactivate owned integrations while preserving state, and existing `TestCaptureLiveDisableStopsWritesAndManualRecoverySurvives` explicitly requires writes and worker renewal to stop. AL-79 must preserve compatible OpenCode consumers and operational disablement while removing per-worktree enrollment prerequisites for native user adoption.
- Trigger: an existing owned legacy integration has a running worker that has not reached its idle deadline. `capture disable --source codex --store STORE --repo PROJECT` succeeds. Source facts then change during that worker's remaining lifetime.
- Consequence: the worker continues collecting and publishing after disable. This is observable modification of a ticket ledger after the user successfully disabled capture, not merely completion of an already committing artifact.
- Trace: `automaticCaptureEnabled` previously delegated to `capture.AutomaticEnabled`, which honors inactive owned integration manifests. C2 returns true after registry existence. The worker fence also removed installation-state checks, and `checkCaptureInstallationScope` bypasses installed-state checks whenever selected local configuration exists. Disabling the old hooks changes none of the remaining eligibility checks. Both legacy harnesses share these worker checks; the executed reproduction uses Codex.
- Reproduction: disposable overlay `TestBehaviorProbeLegacyDisableActiveWorker` installs the real legacy integration, uses a 100 ms refresh with 5,000 ms idle allowance, starts the actual worker and observes publication with input 10. After `capture disable` returns, it waits 350 ms, changes the source to input 30 and observes publication of 30. After another 350 ms it changes source to 50 and observes publication of 50. Cleanup disables local policy and waits for worker completion through existing helpers. This exercises repeated fresh passes after disable.
- Oracle gap: the existing disable/uninstall regression passed, but its fixture registers SessionEnd, uses idle_ms 200 and waits 300 ms before changing source (`capture_corrections_test.go:769`). Normal idle exit can therefore satisfy its no-more-writes assertion even when disable is ignored. A non-idle case detects the regression.
- Required correction: preserve effective legacy deactivation and stop new collection/publication passes without imposing old per-worktree manifests on native user adoption or accidentally disabling a successfully migrated user integration. Strengthen the regression to keep the owner eligible independently of disable until the assertion is made.
